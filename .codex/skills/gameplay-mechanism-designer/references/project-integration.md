# 项目适配：先定输入，再做机制设计

修订：game-project-1 / 2026-09-30。本文约束本 skill 的全部模式和上游输出规范；不替代用户要求、适用 AGENTS 或登记模板。以下代码路径均相对仓库根。本文件的仓库根为 `../../../../`。

## 1. 路由与阅读

- 先确定任务属于主系统、言咒探索或用户明确指定的其他项目。未指定仍为 game-002；调用本 skill 本身不表示启动探索、创建新方向或改写正式规则。安装、审计、方法介绍不需要读玩法正文。
- 只读必要的操作入口：[根手册](../../../../AGENTS.md)、[项目地图](../../../../docs/workspace-map.md)、[Git 协作](../../../../docs/github-collaboration.md)和目标项目 AGENTS。按其职责映射落盘，不在旧兼容目录新建正文。
- **言咒探索在任何游戏正文检索前**先应用 [start.md](../../../../yanzhou/exploration/start.md) 与 [探索 AGENTS](../../../../yanzhou/exploration/AGENTS.md)。新方向默认 CORE，仅 `yanzhou/design/core-design.md`；GDD 使用 start 的固定包；FULL 是已登记主系统文本；CUSTOM 只读显式清单；NONE 不读游戏背景。不要在本 skill 再维护一份 GDD 包清单。
- 开读前报告模式，固定允许文件/章节、实际提交或工作树哈希。已读/未读、范围变更和已有范围外背景写进方向 README；链接不自动扩读，缺材料记 Unknown。不要先全仓搜索再声称只读 CORE。续作沿该方向已登记来源与基线，未经当轮授权不切到新版本。
- 独立肉鸽等其他项目遵循各自注册表和 AGENTS，不自动继承言咒规则、CORE 默认值或历史内容。主系统任务遵循 `yanzhou/AGENTS.md` 的主系统入口；只涉及局部时按该规则缩小范围。
- `references/` 是**通用方法材料**，按模式选择性读取；与游戏背景分开记录。不能通过这些参考文件加载别的游戏项目正文。若用户要求“只用我提供的材料，连方法库也不要读”，不检索内置图谱，只用指定材料；不声称使用了未读链条。

## 2. 模式决定深度，不决定资格

| 模式 | 本项目输出与边界 |
| --- | --- |
| Spark / Domain Scan / Placement Variants / Mechanism Variants / Reverse Design | 生成有不同玩家决策与取舍的 Raw 候选；观察、用户陈述、推断和建议分别标明 |
| Loop Builder / System Network | 补全动作、状态传递、返回条件与失败路径；新补内容是待确认假设，不能给原素材整体升格 |
| Full Design | Raw 阶段仅做构思草案，可沿上游提纲分析；用户要正式 GDD/Proposal 时切到下述资格与登记模板流程 |
| Prototype Pack | 写最小验证计划、观察指标和未执行状态；不因名称或“参数/状态机”等关键词自动实现、启动实验或生成代码技术文档 |
| Audit | 按实际已读范围提出问题和修订候选；不自动修改 current 规则，不把“未读到”写成“设计不存在” |

信息不足仍可探索，但正式资格字段保持 Unknown；模型提出的可行假设不是用户已确认事实。数值建议标“候选值”，未做实验标 Hypothesis / NotRun，不编造有效性或玩法测试结论。只读 CORE 时仅讨论概念关系；NONE 不宣称与言咒兼容。

## 3. 最小落盘

| 目标 | 默认落点 |
| --- | --- |
| 言咒主系统的新点子 | `yanzhou/sources/inbox/YYYY-MM-DD-short-name.md`，使用已登记原始想法模板，Raw Idea / Unqualified |
| 言咒新探索 | `yanzhou/exploration/DIR-NNN-short-name/README.md`，按探索规则分配编号并更新入口一行 |
| 言咒已有方向 | 更新该方向 README，保留原来源、用户原话和已有局部资格 |
| 其他项目 | 按所选项目 AGENTS 的 P/W 路径映射 |

Spark 的三个候选通常是同一主题下的互斥方案，先放**一个方向 README**；用户选择拆成独立方向时再分别建目录。不预建 inbox/materials/proposals/runs 等流程树，不为普通构思更新其他方向或比较表。仅在确需正式文档或支撑材料时在所属方向直接增文件。用户明确要求只讨论、不落盘时遵从。

README 在 start.md 阅读记录后补紧凑内容即可：用户目标/种子 → 候选及取舍 → 推荐理由 → 玩家动作与反馈 → 机制链/循环/系统关系（仅所选模式需要）→ 与所读基准的关系 → Unknown → 下一步与状态。另记“方法来源”：本 skill 上游提交、实际用过的参考文件和链 ID、哪些是原公式/改编/原创。

## 4. 正式设计与实现分流

- 资格确认主动使用 `grill-with-docs`。依照允许输入先查已有答案，缺关键事实一次问一个问题；阅读合同不允许的材料先记缺口，不能以资格确认绕过范围。若该 skill 不可用，报告缺失并保留 Raw，不冒充已完成资格确认。
- 正式素材、GDD、Proposal、Evaluation、Draft Change 使用[根登记模板](../../../../game-design-workflow/templates/README.md)，不以上游 `design-output-spec.md` 替代。GDD 依根流程明确 GDD-0/1/2、审查相关正式素材和 inbox；用户若限制材料，应如实记录未审范围，不能宣称完成全量素材审查。
- 探索资格通过后，正式文件直接放所属方向。回写主系统还需目标项目复审、合格来源与提案/评估、`yanzhou/sources/draft-changes/` 的差异及明确采纳；同步现行规则和决策。局部资格只覆盖原已确认范围，不覆盖本轮新增推演。
- 上游 Full Design / Prototype Pack 中的制作、技术、实现顺序和 telemetry 仅是分析维度。GDD 可写玩家可见状态、设计参数、观察目标及验证标准，不写类、函数、API、代码数据结构、构建命令和实现进度。用户确实要求开发时再读 `yanzhou/development/README.md` 并进入对应代码仓库；其他项目按自身映射。
- 本 skill 不自动安装配套 skill、拉取工具链、联网研究、运行历史脚本或启动玩法测试。实际执行须由用户任务授权；安装本 skill 不构成这些授权。已明确授权的动作按范围继续，不重复确认。

- 原始图谱链号引用为“GMD 图谱 H089”等，避免与项目 `H-YYYY-MM-DD-*` 设计假设混淆；不修改上游链号。引用公式先检查 TSV，改编写明改动，不把框架例子当作已核实产品研究。
- 分类、术语与案例属于通用方法，不覆盖项目对卡牌、状态、冷却等词的正式定义。原文件中的作者和来源署名保持；MIT 通知及固定来源见 skill 根 LICENSE / source-lock.json。
- 交付说明推荐方案、关键取舍、实际材料范围、状态、保存位置与下一步。规则被采纳、玩法成立、实现完成分别报告。
- 遵守项目 Git 保护：修改前检查分支，保护文件同轮提交推送，仅暂存本任务文件，不带入既有未提交变更。不要为技能调用创建并行 agent 或新 chat，除非用户或适用指令明确要求。
