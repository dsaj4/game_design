# GDD 写作标准入口

版本：v1.1。状态：`Reference Ready`。更新日期：2026-09-09。规范来源为[根共享模板索引](../../../game-design-workflow/templates/README.md)及[GDD 写作要求](../../../game-design-workflow/templates/gdd-writing-requirements-and-template.md)，不复制第二份模板。

- 使用前固定本次模板版本/提交，明确 GDD-0、GDD-1 或 GDD-2 完成度。
- 审查本项目 idea-materials 与相关 idea-inbox；inbox 先使用 grill-with-docs 完成资格确认，不能直接写入正文。
- 正文保存到本项目 gdd，记录素材处理和双向来源；探索稿不等于 Accepted。
- 玩家行为、反馈、规则、取舍和设计证据进入 GDD；类、函数、构建、测试命令、Bug 和实现完成度进入代码仓库/原型索引。
- 优化 GDD 回写 game-002 必须先做目标项目适用性复审与 Draft Change。

未列入根索引的模板草稿不能因为本区已建成而自动启用。

## 游戏拆解结果如何进入 GDD

本页是探索区对 game-002 GDD 规范的执行说明。完整章节模板以[根共享 GDD 写作要求与模板](../../../game-design-workflow/templates/gdd-writing-requirements-and-template.md)为唯一来源，本页只说明如何使用它，不复制另一份模板。

游戏拆解报告保持 `Research` 状态。它可以提供外部参考、证据和待验证启发，但不能直接成为项目规则或 `core-concept.md` 内容。只有当启发已经明确为目标项目的玩家行为、规则、反馈、设计价值和验证问题，并通过目标项目的素材资格流程后，才可进入 GDD。

### 1. 选择 GDD 完成度

| 完成度 | 用途 | 必须回答 |
| --- | --- | --- |
| `GDD-0` | 概念对齐 | 一句话概念、目标玩家/情境、体验承诺、设计支柱与反支柱、核心循环、胜负/结束条件、最大风险和最小验证问题 |
| `GDD-1` | 原型验证 | 玩家旅程、原型范围内的系统规格、状态/时序/边界、交互和反馈、规则/体验验收、测试方法、停止信号、风险与决策 |
| `GDD-2` | 制作交接 | 完整系统依赖、内容生产、经济/成长/关卡、引导、UI/无障碍、音画资产、设计边界、异常和回归范围 |

不要求一次写完。只保留当前完成度和已触发模块；不适用章节标为 `N/A`，未知内容标为 `Unknown`。

### 2. 素材审查与状态

建立 GDD 时，先检索目标项目的 `idea-materials/` 和相关 `idea-inbox/`，在 `0. 文档控制` 记录：

| 来源 | 在 GDD 中的角色 | 处理方式 |
| --- | --- | --- |
| 游戏拆解报告 | 外部参考、证据和候选假设来源 | 标明报告路径、证据 ID、版本和适用范围 |
| `idea-materials/` | 已通过资格闸门的正式素材 | `Include / Omit / Park`，建立双向链接 |
| `idea-inbox/` | 未确认原始表达 | 先使用 `grill-with-docs`，不能直接进入正文 |

外部观察转化为本项目内容时，应在项目 `idea-inbox/` 保留触发来源、设计对象、玩家处境与行为、预期反馈、现有关系、未知项和验证方式。字段完整后才晋级 `idea-materials/`。写入 GDD 不会自动改变素材或核心构思状态。

GDD 头部同时记录两种状态：

- 文档成熟度：`GDD-0 / GDD-1 / GDD-2`。
- 设计状态：`Idea / Proposal / Evaluation / Draft Change / Accepted / Parked / Rejected`。

每条设计陈述使用 `Confirmed / Hypothesis / Unknown / Out of Scope`。外部游戏事实属于来源证据；对本项目的借鉴通常从 `Hypothesis` 开始，不能写成 `Confirmed`。

### 3. 分析内容到标准章节的映射

| GDD 章节 | 拆解报告可提供的内容 | 何时填写 |
| --- | --- | --- |
| `0. 文档控制` | 目标项目、版本、成熟度、设计状态、来源、素材审查和变更 | 始终 |
| `1. 产品与体验合同` | 定位、玩家情境、体验承诺、支柱与反支柱 | 始终 |
| `2. 核心循环与玩家旅程` | 核心循环、关键决策、反馈、失败/退出与回流 | 始终；GDD-1/2 补完整旅程 |
| `3. 规则总览` | 术语、不变量、时间/结算单位、系统清单与依赖 | 进入原型或规则讨论时 |
| `4. 系统规格` | 机制、输入、状态、输出、成本、异常、交互、反馈和验收 | 每个当前范围内系统 |
| `5. 状态机与事件时序` | 阶段、响应窗口、优先级、冲突、叠加和取消 | 存在时序、叠加或并发时 |
| `6—9. 数据、卡牌、经济、关卡` | 内容字段、组合、资源流、成长和节点关系 | 对应模块启用时 |
| `10—13. 引导、呈现、音画、边界` | 教学、信息层级、反馈、无障碍、资产和体验依赖 | GDD-2 或原型明确需要时 |
| `14—15. 原型、测试与验收` | 最小验证、规则/体验信号、停止条件和证据链接 | GDD-1/2；GDD-0 写最小验证问题 |
| `16—18. 风险、附录、自检` | 风险、未知、决策、否决方案和提交前检查 | 始终；不适用项写 `N/A` |

### 4. 系统规格的最小闭环

拆解报告中的系统关系进入 GDD 后，先写玩家可理解的链条：

`玩家处境 → 可见信息 → 可选动作 → 决策代价 → 规则结算 → 状态/资源变化 → 感知反馈 → 下一步选择`

每个当前范围内的系统至少说明：设计目的与玩家承诺、输入和触发、前置状态、核心规则、输出和状态变化、成本/限制/取舍、失败/取消/异常、交互和信息反馈、正例/反例、规则验收、体验验收、未知项与依赖。缺少的字段写 `Unknown`，不让实现者自行猜测。

机制、行为和体验分开写：

| 层级 | 应回答的问题 |
| --- | --- |
| Mechanics | 系统允许、禁止和计算什么？ |
| Dynamics | 玩家在这些规则下会形成什么可观察行为？ |
| Aesthetics | 这些行为希望产生什么感受、张力或表达空间？ |

规则验收用 Given/When/Then；体验验收写测试任务、样本、观察项和成功/失败信号。一次演示或一次模拟不能替代体验验收。

### 5. 变更、回写与提交前检查

外部参考形成新玩法候选时，沿目标项目的 `idea-inbox → grill-with-docs → idea-materials → Proposal → Evaluation` 推进。正式核心变更继续使用 `Draft Change → Accepted`，不能从媒体分析或 GDD 直接覆盖 `core-concept.md`。

提交前确认：成熟度和设计状态没有混淆；核心循环包含进入、行动、反馈、失败/退出和再次进入动机；当前系统都有输入、状态、规则、输出与反馈；关键假设有验证方式、成功/失败和停止信号；未知项有影响、负责人和时点；没有把代码实现、构建命令或工程完成度写进 GDD。
