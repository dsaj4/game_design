# 设计评判框架入口

版本：v1.0。状态：`Registry Ready / Proposed Framework / Scoring Not Calibrated`。更新日期：2026-09-09。

本页把[涌现式策略游戏设计框架 v0.1](../../../emergent_strategy_game_framework_v0.1.md)整理成可执行的评估说明。原文是参考框架，不是对任何探索项目的玩法指令；示例、终极目标和公式都必须结合本次项目问题解释。

## 用途与边界

它用于判断一个机制、规则集合、Build、敌人/环境组合或候选玩法是否产生了值得玩家理解和利用的策略空间。评估重点是有效决策、因果关系、取舍、反制和认知成本，不是系统数量、卡牌数量或按钮数量。

本框架可以服务三种对象：

- **具体玩法**：判断一项机制是否有清晰玩家行为和真实取舍。
- **玩法生成空间**：判断结构化规则、AI 候选或内容池能否产生并筛选有效方案。
- **规则涌现系统**：判断简单基础规则组合后是否出现可理解、与目标相关、可主动复现的玩法。

三种对象是评估视角，不是项目必须经历的成熟度等级。game-002 优化与 new-roguelike 都应从自己的问题、背景和证据出发；本页不会把附件中的最终目标写入任何项目核心构思。

## 核心语言

### 五层设计链

使用下面的层级说明候选到底是什么：

```text
Primitive Rule → Interaction → Pattern → Strategy → Meta
```

| 层 | 含义 | 评估问题 |
| --- | --- | --- |
| `Primitive Rule` | 最基础、可复用的规则 | 它改变了什么对象、属性、关系、空间、时间、资源、行动权或信息？ |
| `Interaction` | 多条规则的直接交互 | 哪些规则在什么状态下相互影响？ |
| `Pattern` | 玩家能够识别和复现的重复结构 | 玩家能否把多个结果压缩成一个有用的模式或策略语言？ |
| `Strategy` | 玩家主动利用模式解决目标 | 它改变了哪些选择，支付了什么机会成本？ |
| `Meta` | 策略与敌人、资源、环境和其他策略的关系 | 环境是否会促成适应、反制和策略演化？ |

设计说明可继续使用 `State → Rule → State'` 表达因果变化。对象、属性和关系应按实际项目需要选择，不要求先建立完整物理世界模型。

### 深度与复杂度

策略深度关注玩家能否基于当前和未来状态，在多个有真实机会成本的选项之间做出选择，并通过选择改变后续决策空间。认知复杂度关注玩家需要记住和处理多少信息；增加复杂度不等于增加深度。

评估时优先看：

- 选项的价值是否随状态变化，而非永远固定。
- 玩家是否会比较行动、保留资源、改变路线或承担风险。
- 结果是否能反馈到下一次选择，而不是一次性展示更多信息。
- 玩家经过学习后能否形成描述局面的模式语言。

### 可理解的涌现

好的涌现同时具备：局部规则简单、全局组合有复杂性、玩家可以部分预测、意外结果能够解释和复现，并且结果与玩家目标、资源、风险或决策相关。理想体验是“我大概知道会发生什么”与“原来还能这样”同时存在。

## 评估维度

按候选和问题选择相关维度；没有证据的维度写 `Unknown`，不要用猜测补齐。

| 维度 | 要判断什么 | 需要寻找的证据 |
| --- | --- | --- |
| 强度与成本 | 预期价值是否显著高于投入，是否存在无代价收益 | 成本、结果、状态和对照情境 |
| 状态依赖 | 敌人、地形、资源、Build、阶段或未来风险是否改变价值 | 至少两个状态下的结果差异 |
| 取舍与机会成本 | A 是否在某些方面优于 B，B 是否在另一些方面有理由被选 | 玩家放弃的资源、时间、位置或未来机会 |
| 结果时域 | 选择是否影响后续局面，而不只影响当前数字 | 后续状态、路线或可用行动 |
| 独特性 | 是否创造新的关系或模式，而不只是数值换皮 | 与已有候选的机制差异和交互差异 |
| 协同性 | 是否与已有规则形成有意义的交互 | 交互链、触发条件和新模式 |
| 可反制性 | 对手、环境或资源条件是否能合理回应 | 反制窗口、代价和反制后的新选择 |
| 可学习性与可读性 | 玩家能否理解、预测、复现结果 | 教学、信息呈现、玩家解释、失败原因 |
| 策略贡献 | 增加的是决策深度，还是只增加信息、记忆和 UI 负担 | 有效选择数量、玩家行为变化和认知成本 |
| 退化风险 | 是否形成 dominant strategy、无限循环或单一构筑 | 多状态对照、策略集中度、循环边界 |

强度高不等于设计好。一个候选至少要说明它在哪些情境成立、在哪些情境失效，以及为什么仍值得玩家主动选择。

## 有意义策略检查

把候选称为 `Meaningful Strategy` 前，逐项回答以下问题；这些是评估问题，不是未经校准的硬分数：

1. 玩家是否能理解它为什么有效，并在相似局面主动复现？
2. 它是否只在部分局面有明显价值，而不是所有局面的固定答案？
3. 它是否支付了时间、资源、位置、信息、构筑或未来机会成本？
4. 它是否改变了未来的决策空间？
5. 它是否与其他策略存在可比较的取舍？
6. 环境、敌人或对手是否能以合理成本反制？
7. 它是否具有可记忆的模式，而不是一次随机意外？
8. 玩家是否能围绕它规划、构筑或调整路线？

无法回答的问题保留为 `Unknown`，不通过提高文字描述的复杂度来掩盖。

## 伪涌现检查

以下现象不能单独算作涌现成功：

- 只是排列不同数值，没有新的因果关系。
- 结果纯属随机，玩家不能理解或主动复现。
- 规则复杂但隐藏公式让玩家无法形成因果模型。
- 内容和规则大量增加，只是在枚举更多情况。
- 组合很多但一套策略在多数状态下支配其他选择。
- 模拟结果很复杂，却与玩家目标、资源和风险无关。

报告中应直接指出属于哪种风险，并说明最小验证方式。涌现必须是 **Goal-Relevant Emergence**：它要实际参与玩家目标和决策。

## 高连接规则与涌现效率

评估新基础规则时，优先问它能与多少已有系统产生有意义的交互，而不是只问单独使用是否好玩。高连接不等于自动优秀；连接必须能形成可理解的行为和取舍。

`Emergence Ratio (ER)` 可作为长期方向指标：

```text
ER = Meaningful Emergent Strategies / Primitive Rules
```

ER 只用于比较同一项目、相近范围和明确口径下的候选趋势，不能跨项目直接排名，也不能作为自动接受阈值。记录分子如何定义、哪些策略被计入、哪些证据尚未取得。

## 标准评估流程

1. **登记对象与范围**：记录 Project ID、候选素材/提案、框架版本、要回答的问题和明确不评估的部分。
2. **定位层级**：标记候选属于 Primitive Rule、Interaction、Pattern、Strategy 或 Meta，可同时注明上下游层。
3. **建立因果链**：写清状态、规则、状态变化，以及玩家看到什么、做什么和得到什么反馈。
4. **选择维度**：根据问题选取强度、状态依赖、取舍、协同、反制、可读性、退化等维度，不强行填写不相关栏。
5. **分开证据类型**：分别记录自动模拟/统计、媒体或原型观察、人工判断、玩家解释和未测项。
6. **检查有效策略**：描述至少一个可复现策略和一个反例或失效情境；若材料不足，写 `Unknown`。
7. **检查伪涌现**：排查数值排列、随机噪声、隐藏公式、内容爆炸、dominant strategy 和无目标模拟。
8. **提出验证或结论**：给出最小模拟、原型或人工评议；结论使用 `推进 / 修改后再评估 / 暂缓 / 不建议推进`，并标明依据和限制。

模拟只能说明模型内的结果，不能替代真人对可理解性和趣味性的证据。评估结果写入对应项目的 `evaluations/`，不写入共享目录。

## 状态与项目边界

每次评估记录项目 ID、框架版本、适用维度、自动证据、人工判断和未测项。评估状态与素材资格、GDD 成熟度、核心构思采纳状态分开保存；评估结论不会自动晋级素材，也不会写入 `core-concept.md`。

需要把候选转为正式设计时，沿目标项目的 `idea-inbox → grill-with-docs → idea-materials → Proposal → Evaluation` 推进。优化结果回写 game-002 仍须目标项目复审和 `Draft Change`。框架原文变更后登记新版本，不用新内容覆盖旧评估依据。
