把游戏设计当成一个持续收集证据、做出可观察假设、制作最小可玩版本、测试并调整的过程；文档应随阶段和读者变化而分层，始终能够让团队理解玩家行为、系统规则、成本、反馈和下一步验证。

### 3.1 `M-SJ002-20260904`：从创意到发布

状态：`Reviewed`

来源：`S-SJ002`，`BV1hMNu64E55`，P01-P20，20/20 完成。

本材料要回答的问题：独立开发者或团队如何从概念进入预制作、制作、测试和发布前，并让概念文档、系统文档和功能规格支持实际协作？

#### 一句话结论

先把目标、受众、平台、模式、范围和商业约束说清，再用核心玩法原型验证；进入生产后按项目风险选择瀑布、敏捷或混合节奏，持续测试、调优和记录变更，发布前冻结范围并处理质量问题。

#### 流程/方法抽取

```text
概念 brief/意图
  -> 受众、平台、模式、范围、商业与 IP 约束
  -> 概念文档 + 系统文档
  -> 核心玩法/目标平台原型
  -> 技术评估 + GDD/功能规格 + 美术/团队准备
  -> 瀑布、敏捷或混合生产
  -> 目标问题导向的体验测试与调优
  -> 预发布：范围冻结、修复、打磨、认证、营销
```

#### 设计原则候选

- `DP-CAND-001`：核心玩法先于内容规模。
- `DP-CAND-002`：原型回答一个主要未知，不是展示完整功能。
- `DP-CAND-003`：文档按读者、阶段和功能风险分层。
- `DP-CAND-004`：发布前优先质量收敛，新增内容必须有明确例外理由。

这些仍是 `Candidate`，需要与 `SJ-003`、外部流程来源和本项目测试交叉验证。

#### Agent 规范候选

- `ADRULE-STAGE-001`：触发“开始制作/完整 GDD/发布”请求时，先确认当前阶段、主要未知和退出证据。
- `ADRULE-GDD-001`：写功能规格时，必须拆分子功能并写清触发、状态、规则、输出、反馈和异常；缺失项标 `Unknown`。
- `ADRULE-PLAYTEST-001`：体验测试请求必须声明目标受众、测试目的、版本稳定性、观察字段和下一步决策。
- `ADRULE-SCOPE-001`：进入预发布状态后默认冻结新增系统/内容，任何例外需记录影响与批准人。

#### 最小验证问题

1. 新玩家能否在不读完整规则书的情况下完成一次“抽取/选择/组合/结算”循环？
2. 一份描述单条功能链的 GDD-1，能否让协作者复述输入、代价、效果和失败反馈？
3. 在目标平台上，卡牌信息密度、操作节奏和结算反馈是否支持该循环？

成功信号：玩家完成动作并能解释代价与结果；失败信号：玩家依赖口头补充、把装饰或故事误认为核心机制，或无法指出下一次可尝试的变化。

### 3.2 `M-SJ003-20260904`：游戏测试：游戏设计的核心

状态：`Reviewed`

来源：`S-SJ003`，`BV1ZqN365ERZ`，P01-P30，30/30 完成。

本材料要回答的问题：如何把游戏测试从“找意见”变成有目标、有记录、有反馈闭环的设计方法？

#### 一句话结论

先独自验证可行性，再让别人验证可行性，随后以玩家反应、持续吸引力、简化和打磨为不同目标推进；每次只改变能解释的变量，记录上下文和结果，不把玩家提出的解决方案直接当成设计答案。

#### 测试闭环抽取

```text
确定目标受众与主要未知
  -> 设计最小测试任务和成功/失败信号
  -> 先自己验证，再找代表受众的玩家
  -> 观察行为、提问理解、记录上下文/顺序/结果
  -> 分离问题与玩家方案，识别离群值和替代解释
  -> 一次改一个可解释变量
  -> 重测并更新规则、版本和决策记录
  -> Go / Iterate / Park / Stop
```

#### 设计原则候选

- `DP-CAND-005`：测试先于断言，证据先于自我辩护。
- `DP-CAND-006`：玩家反馈优先作为问题信号，解决方案由设计者负责提出和验证。
- `DP-CAND-007`：一次变更尽量只改变一个可解释变量。
- `DP-CAND-008`：平衡必须按目标玩家、阶段数据和胜利条件定义。
- `DP-CAND-009`：保留放弃、休耕和负反馈作为设计知识。

#### Agent 规范候选

- `ADRULE-PLAYTEST-002`：没有目标问题、受众、任务和成功/失败信号时，不得把一次试玩标记为“验证通过”。
- `ADRULE-PLAYTEST-003`：收到玩家改法时，记录原始问题与建议分开；不得自动采纳。
- `ADRULE-EVIDENCE-001`：测试报告必须列出样本、顺序、环境、离群值和替代解释。
- `ADRULE-BALANCE-001`：涉及对称/平衡时，分别记录起始条件、行动顺序、阵营/策略、阶段结果和目标玩家水平。
- `ADRULE-CHANGE-001`：规则改动后必须登记变更、预期影响和回归范围；无法归因时标记 `Unknown`。

#### 最小验证问题

1. 在短任务中，玩家是否主动比较不同策略？
2. 当某条组合失败时，玩家能否指出是费用、时机、信息不足还是策略判断导致？
3. 记录先手、构筑路线和中场资源后，是否存在某一位置/路线稳定转化为胜利？

成功信号：玩家行为与设计假设一致且仍有替代选择；失败信号：玩家只采用单一安全路线、无法解释反馈，或观察到先手/某组合的稳定优势。

### 3.3 `M-SJ004-20260904`：专业 GDD 写作全攻略

状态：`Partial`。

来源：`S-SJ004`，`BV1pgNZ6JERH`，预期 45 P，成功 44 P；`P005`“记住 3S 和 3C”失败，逐 P 文件不存在，manifest 中 `transcriptChars=0`。P005 的内容、上下文和讲师原始表述均为 `Unknown`，本页不补写其结论。

本材料要回答的问题：如何让 GDD 对不同阶段、不同规模和不同读者有效、易执行、可维护，并在文字、图示、数据库和一页纸之间选择合适载体？

#### 一句话结论

GDD 不是万能模板或一次性圣经；先从目标、概览和大纲建立全局，再按系统、机制、组件和参数拆分，以读者能理解并执行为验收标准，配合流程图、图示、版本记录、同步链接和反馈持续更新。

#### GDD 写作闭环

```text
目标/读者/阶段
  -> 大纲与概览
  -> 系统 -> 机制 -> 组件 -> 参数
  -> 功能规格：输入 -> 状态 -> 规则 -> 输出 -> 反馈 -> 验收
  -> 流程图/图示/一页纸/数据库视图
  -> 队友复述与执行检查
  -> 变更日志、同步引用、回归
```

#### 设计原则候选

- `DP-CAND-010`：文档以读者能理解并执行为验收，而不是以页数或视觉复杂度为验收。
- `DP-CAND-011`：宏观意图先行，低层参数必须可回溯到系统目的与玩家行为。
- `DP-CAND-012`：每个功能形成输入—状态—规则—输出—反馈闭环。
- `DP-CAND-013`：信息只保留一个权威维护位置，重复处用稳定链接或同步引用。
- `DP-CAND-014`：缺失来源保持 `Unknown`，不以标题、相邻内容或个人经验补全。

#### Agent 规范候选

- `ADRULE-GDD-002`：GDD 请求先确认成熟度（GDD-0/1/2）、读者、范围和相关素材，不套用未验证的万能模板。
- `ADRULE-GDD-003`：功能文档必须包含玩家目标/处境、输入、状态、规则、输出、反馈、异常和验收；未知字段显式标记。
- `ADRULE-DOC-001`：任何文档引用变更都必须更新唯一事实源、版本/变更日志和受影响链接。
- `ADRULE-DOC-002`：页面/图表若包含重复事实，必须链接或同步唯一事实源；不同步时不得发布为最终版。
- `ADRULE-EVIDENCE-002`：缺失分集不得被合并稿或课程标题覆盖；相关主题标 `Partial/Unknown` 并列下一步修复。

#### 最小验证问题

1. 另一位协作者能否只读 GDD-1 和一张流程图，复述一回合的输入、费用、时序、结果和失败处理？
2. 同一条规则在 GDD、内容表和测试表中是否只有一个事实源，修改后是否可追踪？
3. 删除一段口头说明后，文档是否仍能让执行者完成最小功能？

成功信号：复述与实现一致，未知项可见，变更能定位；失败信号：依赖作者现场解释、同一参数出现冲突、流程图与规则正文不一致。
