## 一句话结论

一次试玩只有在问题、玩家、版本、任务、观察字段和成功/失败信号都清楚时才是设计证据；记录玩家做了什么与玩家建议怎么改，再通过可解释的变更和回归把反馈带回阶段门。

## 初学者解释

测试不是收集“喜欢/不喜欢”的投票。它要回答一个有限问题，例如“玩家能否理解费用取舍”“先手是否改变了路线”“失败后玩家是否知道下一次可以尝试什么”。同一结果可能由规则、玩家熟练度、测试顺序、设备或环境造成，所以必须记录上下文。

## 测试目的分层

| 测试类型 | 主要问题 | 可接受外观 | 不能推出 |
| --- | --- | --- | --- |
| 自测/可行性 | 规则能否运行、材料是否足够 | 纸面、白盒、手工流程 | 新玩家能理解或喜欢 |
| 可理解性 | 未参与设计者能否复述目标、信息和操作 | 粗糙但可操作 | 长期吸引力或平衡 |
| 体验反应 | 目标玩家是否做出目标动作并获得目标反馈 | 稳定、目的明确 | 所有玩家都适用 |
| 平衡/回归 | 改动是否影响路线、资源、胜率、时长或误解 | 可重复、有基线 | 单局结果就是定论 |
| 边界/质量 | 异常、极端值、失败恢复和可读性是否稳定 | 接近目标版本 | 核心体验一定成立 |

课程把测试拆为渐进目标，并强调不同测试可以穿插；本 Wiki 使用它来补充 `S2-S7`，不把它当成另一套生产阶段（`E-SJ003-P001-001`）。

## 执行步骤

### 1. 写测试合同

```text
Test ID:
Primary unknown:
Target player and recruitment boundary:
Version / rules / placeholder scope:
Player task:
Observation fields:
Environment / order / interruptions:
Success signal:
Failure / stop signal:
Sample boundary and outlier handling:
Next gate or decision:
```

任务写玩家要完成的动作，不提前暗示设计者希望的方案。成功信号应是可观察行为，例如“能指出支付了什么并说明为何保留费用”，而不是“觉得很爽”。

### 2. 先验证可运行，再验证可理解

设计者先走完整流程，记录规则缺口和无法操作的步骤；再让未参与设计的人只看规则和界面完成同一任务。自测不能替代外部测试，设计者熟悉规则也不能证明玩家能理解（`E-SJ003-P002-001`、`E-SJ003-P003-001`）。

### 3. 记录观察，而不是只记意见

| 记录层 | 要写什么 | 不要混入什么 |
| --- | --- | --- |
| `Observed Fact` | 玩家实际动作、犹豫、顺序、退出、口头复述 | 设计者解释 |
| 玩家解释 | 玩家认为目标/问题/因果是什么 | 设计者当作真实根因 |
| 玩家建议 | “改成 X”等方案 | 自动采纳 |
| 设计假设 | 规则、动态或体验的竞争解释 | 伪装成玩家事实 |
| 变更结果 | 改了什么、前后差异、回归范围 | 只报告支持预期的样本 |

玩家通常更擅长指出哪里不工作，不一定能给出可行修复；外部建议既不能因来源而被拒绝，也不能自动变成方案（`E-SJ003-P006-001`、`E-SJ003-P007-001`、`E-SJ003-P028-001`）。

### 4. 保留上下文和离群值

至少记录版本、玩家经验/招募、设备、环境、先后手/座位、顺序、完成/中断和离群值。测试结果同时受游戏、玩家群体和环境影响；单次或无上下文结果只能保持低强度证据（`E-SJ003-P009-001`）。

### 5. 改动前预测，改动后回归

规则、费用、时序、卡牌效果、胜负条件或信息显示改变前，写出预期一阶结果和可能的二阶后果。可拆分时一次只改一个主要变量，用同一任务和字段比较；无法拆分时标为组合实验并保留替代解释。小改动可能改变行动顺序、攻防倾向和战斗频率（`E-SJ003-P010-001`、`E-SJ003-P021-001`）。

### 6. 用证据决定阶段门

| 判定 | 证据状态 | 下一步 |
| --- | --- | --- |
| `Go` | 目标玩家完成目标行为，关键反馈/代价可复述，主要未知已有可接受解释 | 承担下一阶段风险 |
| `Iterate` | 方向可能成立，但有稳定误解、弱反馈或不可解释差异 | 改一个主要假设并重测 |
| `Park` | 可运行但价值/成本暂不匹配 | 保存资产、失败路径和复议条件 |
| `Stop` | 核心动作持续无法产生目标体验或可行性不可接受 | 记录原因、替代解释和不可再用假设 |

一次好评、一次胜负、一个专家玩家或一个平台指标都不能独立决定阶段门。

## 正例与反例

**正例：**“版本 V0.2 只把组合费用提高一个变量。目标玩家为首次接触规则的玩家，任务不变；记录选择率、费用剩余、回合长度、误解和先后手。结果显示等待组合减少但玩家仍能解释代价，下一轮检查战斗反馈。”

**反例：**“试玩后大家都说好玩，所以平衡验证通过。”没有目标问题、样本、上下文、比较版本或失败信号，不能支持任何具体平衡结论。

## 自检清单

- [ ] 测试合同只有一个主要未知。
- [ ] 目标玩家、版本、任务、环境和样本边界清楚。
- [ ] 观察、玩家解释、玩家建议、设计假设和变更结果分开。
- [ ] 失败、退出、离群值和负反馈被保留。
- [ ] 改动前写一阶/二阶影响，改动后有基线和回归范围。
- [ ] 平衡记录包含先后手/路线/阶段数据和玩家熟练度。
- [ ] 阶段门使用 `Go / Iterate / Park / Stop`，不是“验证通过/差不多”。
- [ ] 结论链接到 Test ID、版本、Evidence ID 或明确 `Unknown`。

## Wiki 推断（Inference）

1. 测试合同既是实验计划，也是证据边界；缺少成功/失败信号时，结果不能回答是否应继续。
2. “哪里不对”和“怎么改”分离后，设计者可以提出竞争解释，减少用一张新卡掩盖系统问题。
3. 对卡牌项目而言，路线、先后手、资源阶段和中场领先比单张卡的最终胜率更接近可诊断证据；仍需项目数据验证。
4. 负反馈、退出和停止记录能避免沉没成本驱动的范围扩张，并让未来复议有依据。
