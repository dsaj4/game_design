## 一句话结论

先说明卡牌系统要解决的玩家问题和宏观关系，再把每张卡与每条组合写成输入、状态、时序、费用、输出、反馈和异常的闭环，最后通过记录先手、路线、阶段结果和回归来讨论平衡。

## 初学者解释

卡牌不是孤立的文本。玩家在具体处境中看到信息，决定是否打出、保留、组合或放弃；系统依据状态和时序结算；结果改变资源、风险、胜负和下一次选择。若只写“这张卡造成伤害”，执行者仍不知道何时能用、与什么叠加、失败时发生什么，也无法判断它是否支持目标体验。

### 从宏观到微观

课程建议先看整体游戏和主要系统，再下钻到机制、类别/组件和参数；高层关系会反过来约束低层规则（`E-SJ004-P009-001`、`E-SJ004-P040-001`）。

```text
玩家问题/体验目标
  -> 系统关系与核心循环
  -> 机制与时序
  -> 卡牌类别、组件与组合
  -> 费用、数值、状态和验收
```

不要先填满卡表再寻找玩法。系统尚未可玩时，先用少量明确标记的示例卡验证规则，避免内容返工（`E-SJ004-P032-001`）。

### 一张卡的规则闭环

| 字段 | 初学者要问 | 空白的风险 |
| --- | --- | --- |
| 目的 | 它为玩家解决什么处境或提供什么选择？ | 卡牌只是功能堆积 |
| 输入/前置 | 玩家需要什么信息、资源、标签或状态？ | 结算条件靠口头补充 |
| 费用/代价 | 玩家放弃什么，何时支付？ | 选择没有权衡 |
| 触发与时序 | 何时检查条件，先后还是同时？ | 组合顺序产生争议 |
| 状态变化 | 哪些资源、标记、卡牌或胜负状态改变？ | 无法回归或重复结算 |
| 输出/反馈 | 玩家看到什么结果，下一步能改变什么？ | 玩家不理解自己为何成功/失败 |
| 异常/边界 | 资源不足、目标不存在、取消、重复触发怎么办？ | 实现者各自猜规则 |
| 验收 | 如何证明正常路径和边界路径符合设计？ | “做完了”没有判定 |

### 组合和平衡不是同一个问题

- **组合成立性：** 标签、费用、回合状态和触发顺序是否允许组合，效果是否按预期结算。
- **动态质量：** 组合会诱发什么路线、风险回报和对手反应。
- **平衡：** 在明确模式、胜利条件、玩家水平和测试上下文中，成功机会或努力回报是否合理。

起始条件相同只是**对称**，不等于**平衡**。先手、座位、阵营、构筑路线、玩家水平和阶段性领先都可能改变结果（`E-SJ003-P011-001`、`E-SJ003-P012-001`）。

## 执行步骤

### 1. 写系统目的和玩家处境

在卡表前先写：

> 玩家在【情境】中想达成【目标】，需要在【可选路线】之间取舍；本系统通过【机制/反馈】使这一取舍变得可见。本轮要减少的主要未知是【问题】。

功能规格开头还应写设计支柱、玩家关注点和特殊约束；目标描述“要实现什么”，不只是重复功能名称（`E-SJ004-P007-001`）。

### 2. 建立系统—机制—组件—参数表

| 层级 | 示例问题（不代表项目已定） |
| --- | --- |
| 系统 | 卡牌、资源与反馈如何共同支持所分析游戏的核心循环？ |
| 机制 | 抽取、支付、标签匹配、组合触发、状态持续和胜负判定如何互相影响？ |
| 组件 | 不同卡牌类别、资源与状态分别承担什么角色？ |
| 参数 | 费用、持续回合、目标数量、触发次数和限制如何调优？ |

每个下层定义都要能回到上层目的；无法说明关系的字段标 `Unknown` 或暂时 `Out of Scope`。

### 3. 写单卡和组合规格

采用以下顺序，避免只写结果数字：

1. **玩家目标/处境：** 玩家为何现在考虑这张卡或组合？
2. **输入与前置：** 手牌、费用、标签、目标和回合状态。
3. **触发时机：** 主动、被动、进入阶段、结算后或其他明确时点。
4. **状态与时序：** 先支付还是先检查，多个效果按什么顺序，何时停止或取消。
5. **规则与输出：** 资源、卡牌、生命/胜负、世界收益等改变。
6. **反馈：** 玩家能看到触发原因、费用、结果和剩余选择。
7. **异常与边界：** 费用不足、目标失效、标签重复、效果被打断、回合结束、重复触发。
8. **验收：** 用正常路径和至少一个边界路径写 `Given / When / Then`，并链接测试记录。

复杂功能拆成子功能和子子功能；详细到相关成员可以行动，但仍不写类、函数、API、数据结构或构建信息（`E-SJ002-P010-001`、`E-SJ002-P012-001`、`E-SJ004-P031-001`）。

### 4. 明确组合关系和玩家反馈

组合表至少记录：

| 字段 | 必须回答 |
| --- | --- |
| 组合 ID | 哪些卡牌、标签或状态共同参与？ |
| 成立条件 | 标签、费用、回合状态和动态配置如何共同决定成立？ |
| 结算顺序 | 多条效果先后、同时、替代和停止规则是什么？ |
| 玩家价值 | 它让玩家比较什么，承担什么代价，获得什么反馈？ |
| 失败路径 | 条件不满足时，卡牌是否保留、消耗、退回或产生其他可见结果？ |
| 回归范围 | 改动后哪些卡、路线、资源阶段和胜负结果必须重测？ |


### 5. 设计平衡观察表

讨论“这张卡太强/太弱”前，先收集相同口径的多局记录：

| 维度 | 示例记录字段 |
| --- | --- |
| 起始条件 | 初始手牌、资源、卡组/阵营、地图或遭遇条件 |
| 行动顺序 | 先后手、座位、回合阶段、关键行动顺序 |
| 路线 | 主要组合路线、放弃的选项、资源投向 |
| 阶段数据 | 中场资源、领先转化、组合触发次数、回合长度 |
| 结果 | 最终胜负、成功机会、失败原因和异常中断 |
| 玩家上下文 | 熟练度、测试目的、是否理解规则、环境和离群值 |

多阵营测试尤其要记录行动/座位顺序、阶段分数、最终胜率和中场领先转化；看到稳定偏差后再调规则（`E-SJ003-P023-001`）。单局结果或个人体感不能直接升级为平衡结论。

### 6. 做可解释的变更和回归

变更前写出：

- 改动的主要变量（例如费用、触发时机或某个标签关系）。
- 预期一阶结果和可能的二阶后果（行动顺序、攻防倾向、战斗频率、资源曲线）。
- 对照版本、测试任务和回归字段。
- 无法排除的替代解释。

尽可能一次只改一个可解释变量；必须联动时标为“组合实验”。小改动可能产生大连锁影响，规则书和 GDD 也要同步版本（`E-SJ003-P008-001`、`E-SJ003-P010-001`、`E-SJ003-P013-001`、`E-SJ003-P021-001`）。

### 7. 阶段门：S1-S5

| 阶段门 | 最少证据 | 判定 |
| --- | --- | --- |
| `S1 -> S2` | 一条卡牌行动链有目的、可执行规则和主要未知 | `Go / Iterate / Park / Stop` |
| `S2 -> S3` | 低保真原型能结算，玩家能复述选择、费用和反馈 | `Go / Iterate / Park / Stop` |
| `S3 -> S4` | 代表性体验链包含正常、失败/退出和再次进入，生产方法可复用 | `Go / Iterate / Park / Stop` |
| `S4 -> S5` | 内容与系统在范围内接通，有版本、依赖和回归记录 | `Go / Iterate / Park / Stop` |

“卡牌数量完成”“规则文字写完”或“代码已经实现”都不能单独证明阶段通过。平衡、可读性、无障碍和长期体验需要分别记录。

## 正例与反例

### 正例：一条可回归的组合规则

> `Given` 玩家拥有两张可组合的卡牌，且当前费用达到组合要求；`When` 玩家在主行动阶段选择组合；`Then` 系统先显示将支付的费用，再按预定顺序结算两个效果，并在目标失效时显示组合失败原因。测试记录选择路线、费用变化、结算顺序和下一回合资源。

它写出了处境、前置、顺序、异常和验收；具体数字仍可以保持 `Unknown`。

### 反例：只写强弱和结果

> “这张卡太强，费用改高一点；组合更爽，后面再看平衡。”

反例没有说明对照版本、玩家路线、先手、阶段结果或预期二阶影响，也没有区分组合成立、玩家体验和整体平衡。它不能指导回归，更不能直接作为项目决策。

## 自检清单

- [ ] 卡牌和组合先写系统目的、玩家处境和主要未知，再写参数。
- [ ] 每条规则都有输入/前置、费用、触发、状态、时序、输出、反馈、异常和验收。
- [ ] 复杂功能已拆分，且文档不包含类、函数、API、构建或代码进度。
- [ ] 组合成立性、动态质量和平衡判断没有混为同一结论。
- [ ] 平衡记录包含起始条件、先后手/座位、路线、阶段数据、最终结果和玩家水平。
- [ ] 规则改动写预期一阶/二阶影响、对照版本和回归范围；联动改动标为组合实验。
- [ ] 少量示例卡先于大规模内容生产，系统未验证前不把完整卡表当作进度证据。
- [ ] 失败路径、无法归因的替代解释和 `Unknown` 没有被删除。
- [ ] 阶段门使用 `Go / Iterate / Park / Stop`，项目转化保持 `Hypothesis`。

## Wiki 推断（Inference）

1. **规则闭环比效果短句更能降低协作风险。** SJ-002 的触发/结果/顺序要求与 SJ-004 的输入/状态/反馈/验收要求相互支持；因此一张卡至少要能被另一位协作者按正常和边界路径复述。
2. **卡牌平衡应从动态和上下文观察，而不是从数值直觉开始。** 费用或伤害的改变可能改变保留、抢先、反制和回合长度；先记录路线、阶段和玩家水平，才能知道偏差位于单卡、组合还是时序层。
3. **组合系统的可读性是玩法的一部分。** 玩家必须在做决定时获得标签、费用、触发和失败原因；隐藏规则只有在“隐藏本身是明确设计目的”时才可接受，否则会把不理解误判为策略深度。
4. **内容规模应服从系统证据。** 少量示例卡足以暴露时序、异常和反馈缺口；完整卡池不能替代核心循环验证，也不能用数量证明生产阶段已通过。
5. **单变量是归因工具，不是教条。** 可拆时一次改一个主要变量更容易比较；若组合规则必须联动，应诚实标记为组合实验，而不是把多变量结果伪装成单卡结论。
6. **“平衡”应拆成可检查的目标。** 先定义模式和胜利条件，再分别观察公平的起始条件、机会差异、努力回报、玩家理解和体验质量；“同样起手”或“单局胜负”都不足以覆盖这些目标。

## 未确认信息

- 平衡目标函数、可接受胜率差、样本量、先手补偿、回合长度和玩家熟练度阈值尚未确定；本页不从课程推导具体数值。
- 数字卡牌的 UI 信息密度、动画节奏、网络环境和异步对战影响未由桌游课程证据覆盖。
- `SJ-004 P005` 的 3S/3C 内容缺失，不能用其标题、合并稿或邻集补全任何卡牌/规格规则。
- 本页引用的是逐字稿 Evidence Card 和项目背景，没有独立平衡数据或视觉审查；高风险术语需回看原始分集。
