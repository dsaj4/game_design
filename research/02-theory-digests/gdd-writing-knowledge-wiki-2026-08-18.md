## 3. GDD 的定位：写什么，不写什么

### 3.1 GDD 的四个职责

1. **对齐体验**：团队对“玩家要感到什么、反复做什么”有同一份描述。
2. **定义边界**：明确当前版本做什么、不做什么，避免范围蔓延。
3. **传递规则**：把玩家行为、系统状态、输入、输出、顺序和例外写到可实现程度。
4. **支持验证**：每个关键要求都有原型问题、测试方法或验收条件。

### 3.2 GDD 不应该承担的职责

- 不把所有灵感、参考游戏和未验证数字都写成正式结论。
- 不用形容词替代规则，例如“爽快”“史诗”“智能”“很有深度”必须落成可观察行为和反馈。
- 不在一个大文档里混合愿景、卡牌数据、程序实现、运营配置和测试结果。
- 不把概念图当成可实现的 UI 规格；需要拆成元素、布局、状态和交互。
- 不用一张“看起来完整”的表掩盖未回答的问题。

### 3.3 PRD、GDD、实现规格的工作区分

资料没有给出唯一行业标准，因此这里采用项目工作区分：

| 文档 | 主要回答 | 典型读者 | 完成信号 |
| --- | --- | --- | --- |
| 概念/PRD | 为谁做、解决什么体验问题、为什么值得做、范围是什么 | 制作人、设计、团队负责人 | 一句话卖点、目标玩家、目标体验、成功信号清楚 |
| GDD | 玩家做什么、系统如何响应、规则如何形成动态和体验 | 策划、程序、美术、测试 | 可从文档搭出灰盒原型，关键状态和例外不含糊 |
| Feature Design | 某个功能的完整规则、数据、交互、反馈和内容例子 | 负责该功能的实现者 | 验收标准可转成测试或检查清单 |
| Implementation Spec | 模块接口、数据结构、事件、顺序、持久化和性能约束 | 程序、技术美术、工具开发 | 能独立实现、调试和回放，不依赖口头补充 |
| QA/Playtest Note | 实际发生了什么、玩家在哪里卡住、哪些假设被推翻 | 全团队 | 结论有证据、有改动、有下一轮验证 |

> 本仓库的项目级覆盖规则（2026-08-24）：GDD 只承担上表中的 GDD/玩法设计职责；Implementation Spec、代码架构与开发状态不得写入 `game-design-workflow/gdd/`，统一由 `docs/code-development-index.md` 建立入口，并在对应代码仓库维护细节。

## 4. 从模糊想法到可执行需求

推荐把需求加工成下面这条链，而不是直接跳到“写完整策划案”：

```text
原始想法
  -> 玩家反复动作
  -> 体验承诺与设计支柱
  -> 核心循环
  -> 机制/动态/美学推演
  -> 系统状态与规则
  -> 交互、反馈、内容和数据
  -> 验收标准与原型问题
  -> 试玩证据
  -> 决策记录/下一版需求
```

### 4.1 先写玩家，不先写功能

先回答：

- 玩家在 30 秒、5 分钟、一局、一个 run 和长期循环中分别做什么？
- 玩家在每个节点要做哪一个有代价的选择？
- 玩家如何知道目标、风险、可用行动和结果？
- 设计希望玩家感到紧张、掌控、发现、表达、合作还是沉浸？
- 哪些行为不是本作要追求的？

### 4.2 用 MDA 检查机制理由

每个重要机制至少写出：

| 层次 | 必答问题 | 例子（抽象写法） |
| --- | --- | --- |
| 机制 Mechanics | 规则、输入、资源、限制是什么？ | 每回合只能排列一次手牌；费用在结算前锁定。 |
| 动态 Dynamics | 玩家因此会反复做什么、避免什么、猜测什么？ | 玩家在稳定收益与保留组合之间取舍。 |
| 美学 Aesthetics | 玩家应产生什么可感知情绪？ | 先铺垫、后爆发；失败仍留下可理解的线索。 |

如果只能写出机制，写不出动态和美学，说明需求还停留在功能层。

### 4.3 用术语表消除歧义

术语表应在文档前部维护，并规定：

- 一个概念只保留一个正式名称；同义词写入“禁止混用”栏。
- 区分玩家语言、设计语言和程序语言，确保同一对象在各文档中含义一致。
- 定义时间词：回合、行动、结算、阶段、轮次、run、round、章节。
- 定义状态词：拥有、在手、已激活、已消耗、被禁用、待结算、永久保存。
- 记录单位、范围、是否包含边界值、随机是否可复现。

### 4.4 把形容词改成可观察要求

| 模糊词 | 可执行改写方向 |
| --- | --- |
| 爽快 | 输入后在多少时间内出现何种音效、动画、数值变化和状态反馈？ |
| 易懂 | 新玩家在不读长说明的情况下，能否完成第一项任务？在哪个 UI 点看到提示？ |
| 有深度 | 是否存在至少两种可行策略？每种策略的代价和适用条件是什么？ |
| 随机 | 随机池、抽取时机、种子、保底、不可出现的组合分别是什么？ |
| 平衡 | 哪些策略不应成为唯一最优解？用什么对局样本和指标观察？ |
| 有意义的失败 | 失败后保留什么信息、关系、资源或叙事变化？ |

## 5. GDD 的推荐章节模板

下面是一份适合小团队、卡牌游戏和 AI 协作的最小可执行结构。它不是必须照抄的行业标准，而是一套按风险组织文档的模板。

### 5.1 文档控制

- 文档 ID、负责人、状态、版本、更新时间。
- 关联提案、评估、原型、测试记录和决策记录。
- 本版新增、删除、未决问题。
- 变更影响：规则、数据、UI、程序、存档、测试、内容量。

### 5.2 产品概念与体验合同

- 一句话卖点：玩家在什么情境中做什么独特的事。
- 目标玩家和不服务的玩家。
- 核心体验句：玩家反复做什么并因此获得什么感受。
- 设计支柱：最多 3–5 条，每条都能指导取舍。
- 反支柱：明确哪些看似合理的内容不属于本作。
- 成功信号：行为、反馈、完成率、重玩意愿或试玩观察，不只写收入目标。

### 5.3 核心循环与玩家旅程

用动词写循环，不用名词堆系统：

```text
目标/压力 -> 选择 -> 行动 -> 规则结算 -> 反馈 -> 新信息/新资源 -> 下一选择
```

至少画出：

- 30 秒 onboarding 循环。
- 一次战斗或一次主要交互循环。
- 一局/run 循环。
- 长期成长、世界循环或资产循环。
- 失败、重试、退出和回归路径。

### 5.4 系统规格

每个系统用同一套字段：

| 字段 | 写作问题 |
| --- | --- |
| 目的 | 它解决哪个玩家体验问题？ |
| 玩家承诺 | 玩家为什么愿意使用它？ |
| 输入 | 玩家、系统、随机或其他系统提供什么？ |
| 状态 | 哪些状态会保存、变化、锁定或回滚？ |
| 规则 | 正常流程、限制、优先级、边界值是什么？ |
| 输出 | 资源、信息、事件、动画、音效、下一阶段是什么？ |
| 成本 | 时间、费用、牌位、风险、机会成本是什么？ |
| 失败 | 失败如何表现、是否可逆、失败后留下什么？ |
| 交互 | 玩家具体按什么、拖什么、选择什么、何时能取消？ |
| 可读性 | 玩家在决策前能看到哪些信息？哪些信息故意隐藏？ |
| 内容例子 | 至少给出 3 个代表性实例和 1 个反例。 |
| 验收 | 什么条件下可以说该系统完成？ |
| 未决问题 | 哪些内容暂不决定，如何验证？ |

### 5.5 时序与状态机

卡牌、Buff、事件和经济系统尤其需要写时序。至少明确：

1. 事件何时创建、何时进入队列、何时结算。
2. 多个效果同时触发时按什么顺序执行。
3. 结算中新增效果是否立即插入，还是进入下一队列。
4. 失败、取消、断线、重复点击和重放如何处理。
5. UI 展示顺序是否与规则顺序一致。

可以使用状态表：

| 状态 | 进入条件 | 可用行动 | 自动结算 | 离开条件 |
| --- | --- | --- | --- | --- |
| 选牌 | 玩家获得可用手牌 | 选择/取消/查看信息 | 无 | 点击确认或达到限制 |
| 锁定 | 排列已确认 | 只能查看或使用响应 | 费用与组合检查 | 进入结算 |
| 结算 | 规则队列开始 | 不可修改主行动 | 按事件顺序修改状态 | 队列为空 |
| 结果 | 结算完成 | 查看反馈/选择后续 | 发放奖励或失败结果 | 进入下一节点 |

### 5.6 数据表和内容规范

把高频变化内容从正文拆到数据表，正文写字段语义和约束。每条卡牌/事件至少包含：

- ID、名称、类型、标签、稀有度、解锁条件。
- 目标、费用、基础效果、组合条件、触发事件。
- 结算优先级、持续时间、叠加规则、冲突规则。
- UI 文本、图标、颜色、音效、动画和可访问性信息。
- 可出现的池、不可出现的池、测试种子或示例局。

## 6. 验收标准：让需求真正可测试

### 6.1 每个功能至少有三类验收

1. **规则验收**：状态、数值、顺序、边界和持久化正确。
2. **体验验收**：玩家能理解目标，能看见反馈，核心感受与支柱一致。
3. **交付验收**：可运行、可复现、性能/输入/存档/兼容性满足范围。

本仓库应用时，GDD 只保留规则验收和体验验收；交付验收属于开发进度与实现仓库，不进入 GDD 正文。开发完成也不能自动把设计假设升级为已确认结论。

### 6.2 Given/When/Then 写法

```text
Given 玩家满足动作前置条件并拥有足够资源
When 玩家在允许的状态确认动作
Then 系统按明确顺序结算代价与结果，并显示反馈
And 若任一条件不满足，系统按约定保留状态并说明阻断原因
```

### 6.3 不可变条件与负例

除了“应该发生什么”，还必须写：

- 不应发生的组合。
- 费用不足、重复触发、目标已死亡、状态过期时的结果。
- 玩家快速重复输入、退出重进、加载旧存档时的结果。
- 随机池为空、内容缺失、资源超上限时的降级策略。

负例是 AI 实现和 QA 最容易发现差异的地方，不能只写在口头讨论里。

## 7. 原型、试玩与反馈如何回写 GDD

### 7.1 一个原型只回答一个主要问题

原型问题应写成可判定句，例如：

- 玩家是否愿意主动尝试不同的行动方案？
- 一次响应窗口是否足以产生互动，而不会变成长连锁？
- 系统反馈是否会改变玩家下一次选择？

同时写停止条件：什么观察结果会让我们删除、缩小或重做方案？

### 7.2 原型分层

| 原型层 | 目的 | 可使用的材料 |
| --- | --- | --- |
| 纸面/表格 | 验证循环、资源、收益矩阵、组合数量 | 卡片、骰子、Excel |
| 灰盒 | 验证输入、空间、节奏和可读性 | 方块、默认 UI、占位图 |
| 手感 | 验证反馈、动画、音效、响应窗口 | 简单特效、镜头、音效 |
| 内容 | 验证卡牌、事件、关卡的组合质量 | 少量代表性内容 |
| 试玩版 | 验证前 5–15 分钟和留存 | 可发布构建、问卷、行为记录 |

### 7.3 反馈的证据优先级

建议按以下顺序解释反馈：

1. 玩家实际行为：卡在哪里、重复做什么、主动忽略什么。
2. 玩家原话：他们觉得哪里不懂、哪里不爽、哪里想再来一次。
3. 设计者推断：行为与原话共同支持的原因。
4. 改动假设：准备改变哪个变量，预期改变什么行为。

玩家通常擅长指出问题，不一定能给出正确解决方案；不要把“玩家说要地图”直接等同于“增加地图就是解法”。

### 7.4 GDD 的变更纪律

- 已验证结论、待验证假设、暂缓想法分开写。
- 每次改动记录来源、动机、受影响模块、验证方式和回滚条件。
- 如果改动冲突设计支柱，必须显式写出取舍。
- 原型否决的内容保留在研究/提案/决策记录中，不要静默删除。

## 8. 卡牌、经济、关卡和系统实现的专项写法

### 8.1 卡牌 GDD

卡牌不是“效果文本列表”。每张牌应说明它在循环中的决策位置：

- 玩家什么时候看到它，为什么此刻在意它。
- 它改变哪个资源、风险、节奏或信息关系。
- 它与核心机制的组合入口是什么。
- 它的最佳使用场景、可接受的次优场景和错误用法是什么。
- 它与同类牌的区分依据是什么，而不是只靠更大的数字。
- 新手初始牌组如何用重复和低复杂度建立词汇。

卡牌构筑类肉鸽尤其要避免“复制同一套基础攻击/防御牌再换主题”。应先定义独特的核心机制，再让卡牌围绕该机制产生新的决策。普通牌要有早期价值，稀有牌可以更强但不应替代整个构筑逻辑。

### 8.2 经济 GDD

先画资源流，再写价格：

```text
来源 -> 持有 -> 转换/交易 -> 消耗 -> 回收/销毁
```

每种资源写清来源占比、主要消耗、可储存上限、时间价值、稀缺节奏、替代品和玩家信任风险。货币越多不等于系统越深；每新增一种货币，都要说明它解决的独特问题。

### 8.3 关卡和世界 GDD

不要把关卡写成“玩家先去 A，再去 B”。应写空间提供的选择和后果：

- 至少两种可行路线或流派解法。
- 主线如何支持不同构筑，支线如何整体平衡。
- 关键地标、可见目标、留白和喘息区。
- 固定锚点遭遇与移动/随机遭遇的职责。
- NPC 的可预测性与潜行/战斗的关系。
- 探索回报和失败后的世界变化。

### 8.4 Buff、组合和事件实现 GDD

把规则层写成“事件 + 队列 + 插件”，而不是把所有效果塞进主流程：

- 事件节点：回合开始、行动确认、造成/受到效果前后、回合结束。
- 监听者：Power、组合效果、遗物、世界修正器。
- 数据包：输入值、来源、目标、标签、可修改字段。
- 顺序：优先级、同优先级排序、是否可重入。
- 输出：规则结果、日志、表现事件。

规则核心应能脱离引擎测试和回放；引擎层只负责表现、输入和展示。新增效果应尽量通过新增数据/插件完成，而不是修改一条巨大的条件链。

## 9. AI 协作写 GDD 的方法与风险

资料中的 AI 工作流共同指向一套原则：AI 可以扩展需求、生成初稿、拆任务和检查遗漏，但人必须拥有体验判断和最终取舍。

### 推荐流程

1. 人先给出粗略想法、目标玩家和不可妥协的体验。
2. 策划 Agent 用问答追问玩家动作、规则、边界和验证方式。
3. 独立审计 Agent 检查术语、遗漏、冲突、不可测试表述和范围蔓延。
4. 人确认设计文档和优先级。
5. 将总纲拆成正交模块：核心循环、内容数据、经济、程序实现、UI/美术、QA。
6. 分阶段实现，每阶段只读取相关上下文。
7. 真实运行、自动测试、视觉检查、修复、归档。

### 必须防止的 AI 失败

- 文档过于泛化，生成的游戏自然同质化。
- AI 自动补全了未确认的规则，把猜测伪装成需求。
- 一次性塞入过多任务导致上下文丢失。
- 概念图被误当成布局、交互和状态规格。
- AI 生成了看似统一但缺少可读性的卡牌、颜色或 UI。
- 没有验收标准，最后只能凭“感觉差不多”收尾。

### 给 AI 的最小输入包

- 当前版本范围和明确不做项。
- 术语表和数据单位。
- 玩家旅程、核心循环和设计支柱。
- 模块接口、状态机、时序和数据表。
- 正常例子、边界例子、负例。
- Given/When/Then 验收标准。
- 参考图的用途、版权边界和布局拆解信息。
- 当前未决问题，不允许擅自决定的事项。

## 11. 一页式 GDD 自检清单

提交一版需求前，逐项回答“是/否/证据”：

- [ ] 一句话能说清玩家反复做什么和独特之处。
- [ ] 目标玩家、目标情绪和反支柱已写明。
- [ ] 核心循环使用动词，并标出反馈和下一选择。
- [ ] 每个关键机制都完成了机制→动态→美学推演。
- [ ] 术语、单位、时间词和状态没有多义。
- [ ] 规则、输入、输出、顺序、边界和负例已写明。
- [ ] UI 能在决策前给出必要信息，并定义颜色/图标层级。
- [ ] 卡牌/事件/资源的数据字段可直接转成表格或配置。
- [ ] 需求有 Given/When/Then 或等价验收标准。
- [ ] 至少有一个低成本原型问题和停止条件。
- [ ] 试玩反馈按行为、原话、推断、改动假设分层记录。
- [ ] 版本范围、不做项、风险、未决问题和变更记录齐全。
- [ ] 若由 AI 实现，已提供完整输入包并安排运行/视觉/回归检查。

## 14. 最短实践路径

第一次写一个功能时，只做四件事：

1. 用一句话写玩家要做的事和为什么在意。
2. 用一张状态/时序表写正常路径、边界和负例。
3. 用一条 Given/When/Then 写验收条件。
4. 用一个低成本原型验证最危险的假设，并把结果回写文档。

这四步比堆叠几十页背景设定更能判断一个 GDD 是否真的可用。
