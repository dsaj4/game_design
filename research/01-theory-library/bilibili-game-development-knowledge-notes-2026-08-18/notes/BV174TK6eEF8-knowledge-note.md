# GODOMAKER：用自然语言驱动AI自动开发游戏的工作流

## 核心结论

GODOMAKER是一套免费开源的游戏开发工作流，核心思路是让用户只通过自然语言描述游戏想法，由AI编码代理（如Codex）自动完成从设计、开发、美术生成到测试修复的完整闭环。在视频演示中，作者与Codex沟通20分钟，Agent自动工作5小时，便做出了类似《杀戮尖塔》的卡牌游戏初版。这套流程的关键在于精心设计的设计文档：策划Agent通过多轮问答发散创意，再由独立审计Agent二次检查，最终生成分阶段任务规划。这样的设计大幅降低游戏开发门槛，也让“人人做游戏”成为可能。

## 关键概念与前置准备

### 编码代理（Coding Agent）
工作流必须依赖一款编码代理，支持Claude Code、Codex或OpenCode三选一，且需要具备相应的订阅或API key。

### 基础环境
- Godot引擎（4.x版本）
- Node.js
- Git

安装GODOMAKER CLI后，通过指令启动即可创建项目。作者提示，也可以直接将GITHUB链接发给Agent，让Agent自动完成安装。

## 工作流分阶段讲解

### 1. 项目初始化
在GODOMAKER CLI中输入`start`，工具会自动创建项目并下载最新的GODOMAKER skills。随后需要指定本地Godot引擎路径。项目目录下有一个`CONFIG`文件，可配置各阶段使用的大模型。这里有两个关键约束：
- VQA模型必须是视觉模型
- asset模型必须是能生成图像的模型

支持的模型都写在配置文件的注释里。完成配置后，Codex就会调用GODOMAKER skill开始制作游戏。

### 2. 设计文档：策划问答与审计
这是整个流程中最核心的环节。设计文档的质量直接决定产出游戏的独特性与趣味性。流程是：
1. 策划Agent先向你询问核心点子（可以是非常粗略的想法）；
2. 策划Agent围绕点子进行多轮问答发散，把模糊概念细化；
3. 随后启动一个独立的审计Agent对文档进行二次检查，找出疏漏、补充细节；
4. 用户可在此时查看审计结果并提出修改意见，确认后方案进入下一阶段。

在视频演示中，作者为录制效率让审计Agent自行决定答案，最终生成完整设计方案供用户确认。

### 3. 任务规划与迭代
方案确认后，策划Agent会生成设计文档和任务规划，保存为本地文件，后续所有开发Agent都会严格按这两个文件工作。Agent会主动把整个游戏开发拆分为多个阶段，并建议分轮迭代。原因是一次性交办过多任务容易导致“上下文腐烂”，即Agent在处理大量信息后丢失早期关键上下文，从而降低成功率。分轮迭代能有效规避这个问题。同时，Agent在每一阶段开始时，都会读取当前阶段所需的上下文，确保信息聚焦。

### 4. 自动化开发与美术资源
进入自动化开发阶段后，开发Agent会根据任务间的依赖关系和优先级，将子任务派发给子Worker实现。美术资源（如卡牌图片、UI素材）不需要人工制作，全部由AI使用配置好的生图模型自动生成。

### 5. 测试修复与验收归档
基础功能完成后，可用性校验会先行跑通。接着测试员Agent会编写测试代码，真实运行游戏，并做视觉检查。发现问题后，由修复Agent自动循环处理，直到验收通过。验收后Agent会进行收尾和归档，此时用户可以通过Godot引擎直接运行游戏，或使用指令启动。

## 使用建议与限制

- **保持设计文档的独特性与完整性**：文档越独特、越完整，产出的游戏越有趣。泛泛而谈的设计会得到平庸的结果。
- **避免一次性任务堆积**：必须分阶段迭代，防止上下文腐烂。
- **模型选型必须匹配**：VQA模型必须是视觉模型，否则无法完成视觉检查；asset模型必须支持生图，否则无法生成美术资源。
- **问题修复策略**：运行游戏时发现的简单问题，可以直接用Coding Agent对话修复；复杂问题则建议启动新一轮GODOMAKER迭代流程。

## 结论与影响

GODOMAKER展示了一种“自然语言→完整游戏原型”的高效工作流。它把传统游戏开发中的设计、策划、程序、美术、测试等环节，全部交给经过编排的AI代理协作完成，而人类只需提供创意和关键决策。对于独立开发者和游戏爱好者来说，这大大降低了游戏制作的门槛。同时，它也将“AI辅助开发”从单点补全推进到了多智能体协作的全流程流水线阶段。
