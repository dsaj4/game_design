《暂定名：言咒》核心系统 GDD v0.1
文档类型： Game Design Document / Core Combat System
游戏类型： Roguelike + 构筑 + 背包/槽位管理 + 组合式施法
核心幻想： 玩家不是“使用法术卡”，而是掌握一套逐渐扩展的魔法语言，通过组织词汇、语法和语义创造法术。
1. High Concept
玩家在 Roguelike 流程中不断获得新的词汇、语法规则、修饰词和语言能力，并在有限的词槽、字数和战斗资源约束下，通过组合：
主语 + 谓语 + 宾语

生成法术。
核心区别不是：
三张卡同时触发三个效果。

而是：
三个不完整的语义组件共同构成一个新的完整效果。

因此：
传统卡牌：
Card A → Effect A
本作：
Subject + Operator + Operand → Generated Spell
例如：
火焰 + 吞噬 + 护甲

并非：
火焰造成伤害 + 吞噬回血 + 护甲加盾

而是：
获取目标护甲 → 吞噬护甲得到数值 N → 火焰接收 N → 按火焰规则结算。

2. Design Pillars
P0｜支柱一：Composable Language——真正的组合式语言
这是整个项目最不可妥协的核心。
主谓宾不是三张独立卡牌，而承担不同程序职责：
成分	系统职责	抽象
主语	定义效果如何进入世界	Context / Actor
谓语	定义发生什么操作	Operator
宾语	提供被操作的数据	Operand
修饰词	改写上述组件	Modifier


基本模型：
Spell =
Verb(
    SubjectContext,
    ObjectOperand
)
设计验收标准：
单独拿出任何一个词，它都不应该构成完整的卡牌效果。

如果“火焰”“吞噬”“护甲”单独都可以正常使用，那么系统已经退化为卡牌效果叠加。
P0｜支柱二：World as Language——战场本身就是语言素材
玩家不是只对“敌人”施法。
战场中的：
生命
护甲
力量
燃烧
中毒
敌人的下一次攻击
正在吟唱的法术
召唤物
上一句咒语
……
全部可以成为语言引用对象。
因此战斗循环是：
世界产生对象 → 玩家用语言重新组织对象 → 世界改变 → 产生新的可引用对象。

而不是：
出牌 → 扣血 → 出牌 → 扣血。

P0｜支柱三：Constraint Creates Expression——限制创造表达
玩家不能无限造句。
核心限制包括：
词槽 + 字数 + 当前词汇 + 战斗时间/行动资源
因此同一个问题可以产生不同语言解法。
例如敌人拥有 15 护甲：
火焰 吞噬 护甲

或者：
我 窃取 护甲

或者：
护甲 转化 燃烧

后期甚至：
影子 模仿 上一句法术

玩家的 Build 本质上决定：
“我擅长用什么语言解决问题？”

P0｜Active Vocabulary
玩家拥有完整词典，但战斗中只有一部分词处于“活跃/可调用”状态。
例如：
主语槽 × 3

燃烧

玩家通过战斗机制进行：

来改变当前可用词。
设计目的
保留 Roguelike 的随机性，同时避免：
抽到 3 个主语 + 2 个宾语，完全无法组成句子。

6. Spell Construction System
6.1 基础语法
P0
初始 Grammar：
Subject → Verb → Object
即：
主语 + 谓语 + 宾语

例如：
火焰 吞噬 护甲

7. Semantic Type System
P0｜语义类型
所有词拥有 Type，而不是只有“卡牌类别”。
首版建议只做五类：
Type	示例
Entity	我、敌人、火焰、影子
Property	生命、护甲、力量
Status	燃烧、中毒、冻结
Value	伤害量、失去生命量
Spell	上一句法术、敌人的法术


其中 Spell Type 是非常重要但实现风险较高的类型。
因此建议：
Entity / Property / Status = P0
Value = P1
Spell = P1
不要一开始全部实现。
8. Subject System
P0｜主语 = Resolution Context
主语不只是 Target 或元素标签，而决定：
运算结果最终如何被结算。

例如：
火焰
Value
↓
转化为 Heat
↓
造成火焰效果 / 燃烧
影子
Effect
↓
记录
↓
在特定条件再次执行
我
Value
↓
直接作用于玩家属性
首个原型建议只实现 3–4 个行为高度不同的主语。
否则测试组合空间会迅速失控。
9. Verb System
P0｜谓语 = Operator
谓语是整个组合系统最重要的内容。
建议内容制作投入大致：
主语 25% / 谓语 50% / 宾语 25%

谓语不是：
造成 10 点伤害。

而是：
对某种输入执行某种转换。

首版候选：
谓语	Operator
伤害	Apply
获得	Add
失去	Remove
吞噬	Consume → Convert
转移	Transfer
交换	Swap
复制	Copy
转化	Convert
放大	Multiply


例如：
Consume(Property)
→ Remove(Property)
→ Output Value
随后由 Subject 决定 Value 如何结算。
10. Object System
P0｜宾语 = Operand
宾语不是简单 Target。
它可能提供：
对象
敌人

属性
护甲

状态
燃烧

数值
受到的伤害

法术
上一句法术

例如：
我 + 窃取 + 护甲

解析：
Armor → Steal → Player
而：
火焰 + 吞噬 + 护甲

解析：
Armor
↓
Consume
↓
Value
↓
Fire.Resolve(Value)
因此同一个宾语在不同谓语下具有不同意义。
11. Semantic Compatibility
P0｜类型兼容
不是所有句子都应该合法。
例如：
吞噬:
Accept:
Property
Status
Resource
因此：
火焰 吞噬 护甲 ✓
火焰 吞噬 燃烧 ✓
火焰 吞噬 敌人 ✕

这实际上构成：
语言系统的规则边界。

玩家需要学习这些规则。
12. Modifier System
P1｜修饰词
修饰词不是单纯：
+30% Damage

而应该修改 AST / Operator。
例如：
所有
SingleTarget
→
Collection
再次
Operator
→
Repeat(Operator)
缓慢地
Immediate
→
OverTime
所以：
火焰 缓慢地 吞噬 所有 护甲

可以编译成：
OverTime(
    Consume(
        Fire,
        All(Armor)
    )
)
13. 字数系统
P0｜Language Capacity
每个角色拥有：
最大句长

例如：
6 字。
玩家必须在限制内完成表达。
简单：
火 吞噬 甲

复杂：
永恒火焰反复吞噬所有护甲

可能无法使用。
设计意义
字数不是单纯 Mana，而是：
Spell Complexity Budget

14. 战斗资源
推荐最终存在三类不同限制，但原型阶段不要全部上线。
P0｜字数
控制：
单个法术复杂度。

P1｜专注 Focus
控制：
连续施法能力。

P1｜时间 Time
控制：
施法速度与敌我行动关系。

三者分别回答：
能说多复杂？

能说多少次？

来不来得及说？

15. Combat Timeline
P1｜时间轴战斗
最终版本推荐使用 Timeline，而不是传统轮流行动。
例如：
0────1────2────3────4────5
玩家      敌A      玩家   Boss
每句法术具有 Casting Time。
短句：
火 攻击 敌人

可能 Cost = 2。
长句：
永恒火焰反复吞噬所有护甲

可能 Cost = 5。
因此：
表达能力 ↔ 时间压力

形成直接关系。
不过我会明确把它降到 P1。
因为第一版原型如果同时验证：
语言系统 + 时间轴

你会不知道“不好玩”究竟是哪套系统造成的。
16. Enemy Design
P0｜敌人提供“语言问题”
敌人的核心职责不是制造更大的数字，而是产生值得操作的世界状态。
基础敌人：
高护甲
强化自己
施加中毒
准备强攻击
生成召唤物

让玩家寻找不同语言解法。
P1｜语言攻击型敌人
中后期敌人可以直接攻击玩家语言系统。
例如：
缄默者
封印一个谓语。

删字者
暂时降低最大句长。

扭曲者
改变下一句语序。

遗忘者
使某个活跃词暂时失效。

这些非常符合主题，但不应该在最早原型阶段开发。
因为它们属于：
系统对系统的 Meta Interaction

必须等基础语言已经好玩。
17. Enemy Intent
P0
敌人应该公开下一步行为：
3 时间后：
攻击 12

状态：
护甲 8
燃烧 3

准备：
强化力量
其设计目的不是单纯方便玩家防御。
而是让敌人的：
状态、属性、意图

成为玩家构句时的 Operand。
例如：
时间 延迟 攻击

影子 复制 强化

18. World State Feedback Loop
P0｜这是战斗系统第二重要的机制
法术产生的新状态必须能够继续参与下一次施法。
例如：
第一句：
火焰 攻击 敌人

产生：
燃烧 = 4
第二句：
影子 复制 燃烧

第三句：
我 转移 燃烧

也就是说：
Spell
↓
World State
↓
New Operand
↓
Spell
如果这条链不存在，那么玩家最终仍然只是在不断：
拼一句话 → 造成伤害。

19. Linguistic Context / 连句系统
P2｜语境继承
连续法术可以共享 Context。
第一句：
火焰 攻击 敌人

记录：
Subject = Fire
Target = Enemy
下一句：
吞噬 护甲

自动解析为：
火焰 吞噬 敌人的护甲

于是多条 Spell 可以形成：
语段 / Paragraph

例如：
火焰攻击敌人。
吞噬护甲。
再次攻击。
扩散燃烧。
这是非常有潜力的系统，但明显属于第二阶段扩展。
20. Grammar Build
P2｜语法构筑
默认：
SVO
但遗物/能力可以修改 Grammar。
例如：
省略主义
允许：
V + O
继承上一句 Subject。
双宾语
允许：
S + V + O + O
倒装法典
允许：
O + S + V
无主句
允许：
V + O
但产生特殊风险/奖励。
这意味着 Roguelike Build 不只是收集词，而是在修改：
这门语言本身。

非常有特色，但建议 P2。
21. Rule-Breaking Relics
P2
遗物最好不要大量设计成：
火焰伤害 +20%。

而应该修改系统规则。
例如：
《异端语法》
“吞噬”现在可以接受 Spell 类型。

《速记术》
每句话第一个修饰词不计入字数。

《无声咏唱》
三字以下法术施法时间 -1。

《复述法典》
每三句自动重复第一句。

这会形成真正的：
Rules Build

22. Language Degradation
P3｜语言能力退化
这是非常有表现力，但实现与平衡成本很高的机制。
Boss可以逐渐破坏：
字数
词汇
语法
记忆
修饰能力

于是玩家战斗初期可能说：
灼热的火焰迅速吞噬所有护甲

战斗末期只能：
火 攻击 人

这种“语言退化”非常适合 Boss 或特殊关卡，而不适合作为基础系统。

25. MVP最关键的测试指标
不要首先测“平衡”。
首先测四件事。
A. 组合是否真的产生涌现？
玩家有没有出现：
“等等，【吞噬】居然可以这样用？”

这是最高价值反馈。
B. 不同句子的决策是否真正不同？
如果：
火焰攻击敌人
影子攻击敌人
我攻击敌人

最终只是：
8伤 / 10伤 / 12伤

则核心系统失败。
C. 世界状态有没有成为资源？
理想玩家应该出现这种思考：
“我现在故意不给敌人清掉燃烧，因为下一句可以吞噬燃烧。”

这说明战斗系统和语言系统已经闭环。
D. 玩家是在“造句”还是在“算卡牌”？
这是最关键的体验指标。
理想情况应该是：
“我想把他的护甲转成燃烧，再让影子复制燃烧。”

而不是：
“这三张牌 DPS 最高。”

前者说明玩家已经开始用语言语义模型理解游戏。
26. 当前项目的真正核心，可以浓缩成四层
如果现在需要决定哪些东西绝对不能砍，我会只保留：
第一层
词汇
Subject / Verb / Object
        ↓
第二层
语义
Type / Operator / Operand
        ↓
第三层
世界
Enemy / Property / Status / Resource
        ↓
第四层
反馈
Spell → World → Operand → Spell
其中最核心的循环不是“主谓宾”本身，而是：
【观察世界】→【发现可操作语义对象】→【组织语言】→【改变对象之间的关系】→【产生新的世界状态】→【新的世界状态成为下一句话的材料】。

这句话可以直接作为目前整个战斗系统的核心设计声明。
而“修饰词、时间轴、倒装、遗物改语法、语境继承、语言退化”虽然都很好，但本质上都是围绕这个循环的扩展层。如果 P0 不好玩，P1–P3 加得越多，项目反而越难救；如果 P0 已经好玩，后面这些机制会非常自然地长出来。
