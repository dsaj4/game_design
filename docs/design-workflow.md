# 设计流程与资格规范

状态：现行操作规范 / 2026-10-23。由原根AGENTS的流程收束而来，资格与采纳门槛不变。先按目标项目AGENTS选择W/P和允许材料；以下言咒路径不适用于独立肉鸽。

## 言咒轻量记录

2026-10-23起生效，依据[G002-DOC-027](../yanzhou/governance/decision-log.md#g002-doc-027)。以下约定覆盖言咒入口、共享模板和旧规范中要求重复留档的字段：

- **输入只留摘要。** 用简短文字记录用户意图、已确认决定及适用范围，未知单列；不保存逐字原话、聊天转录或逐题问答。不要求另建原话文件、消息ID或资格过程表；已有正文能说明资格时直接引用，不再抄写一份清单。模型建议仍须与用户决定分开。
- **版本只登记一次。** 同轮材料共用一个完整Git提交号，条目引用准确的文件、章节或规则ID；已有版本入口可直接引用。不重复逐文件blob或哈希清单。不同仓库／版本分别注明；只有实际使用的未提交文件或无法固定版本的外部快照才补哈希。输入版本不会随分支移动自动更新。
- **来源只留必要关系。** 在使用处写“结论或变更 → 来源定位”，继承共同版本；只记录实际采用和仍影响决定的待定／冲突。无需复制库存、逐轮审查过程、空表或双向使用台账。当前规则引用其采纳依据；追因时再沿链接查来源。未读来源不能宣称已核实。
- **验收只留可判断内容。** 设计侧保留“情境／操作 → 预期结果＋规则引用”，可直接引用已有案例；执行侧保留“结果／状态＋固定证据链接”，不向GDD复制日志、截图目录和历史轮次。共同状态与范围写一次，仅例外单列；未运行保持NotRun。合并重复项时保留独有失败情境及既有引用定位。
- **核对聚焦一致性。** 检查同轮版本是否一致、引用是否存在且支持所述结论；只报告不一致、缺失与待决项，不另写审查过程报告。规则采纳、实现和体验证据的状态仍分别如实表达。

这些约定简化记录，不增加采纳或测试授权。现有历史不批量重写；整理当前页时可将独有结论合入正文，旧过程按固定Git取证，不另建迁移清单。记录保留在所属文档，不新建平行台账。

## 批量澄清

用户2026-10-01要求将每次单题确认改为一次尽可能处理多个问题。本规则适用于本仓库的常规澄清、资格确认、GDD素材选择、阅读范围确认，以及`grill-me`／`grill-with-docs`调用；它覆盖技能上游的逐题等待默认，仅在本项目生效。

- 先从本轮允许材料解决已有答案，再把需要用户决定的问题按主题、优先级和依赖分组；一次提出当前可以有效回答的尽可能多项，不设置固定单题或固定题数上限，也不把无关库存塞进问卷。
- 每项使用稳定编号，写明问题、推荐答案、简短理由或影响；选项仅在确有不同选择时提供。允许按编号回答、只纠正少数项，或明确回复“本批全部按推荐”。
- 能独立决定的问题同批提出；后续选项受前项影响时，先明确条件分支并同批展示。只有当前答案会使后续问题失去意义或需要重写时，才留到下一批；不为凑批量猜定前提。
- 用户只回答部分时只确认对应项，未回答、含糊或跳过的内容保持Unknown；沉默和模型推荐不算采纳。“本批全部按推荐”只覆盖本批已明确列出的推荐与适用条件，不授权未列出的后续选择；互斥或条件冲突仍需澄清。
- 收到回复后逐项记录已确认、暂缓、未知及来源，推进不受缺口影响的工作；下一批只追问余下缺口和新产生的依赖，不重复询问已明确答案。
- 批量回答不扩大READ-1材料权限、不跳过资格或正式采纳流程。范围增补可集中列出所需文件与用途，但未获明确授权前不读取。用户明确希望慢速单题时按其当轮偏好执行。

推荐格式：

| 编号 | 待确认问题 | 推荐答案 | 理由／影响 | 依赖 |
| --- | --- | --- | --- | --- |
| Q1 | 〈问题〉 | 〈推荐〉 | 〈简短理由或取舍〉 | 无 |
| Q2 | 〈另一问题〉 | 〈推荐〉 | 〈简短理由或取舍〉 | 若Q1选A则适用；否则暂缓 |

编号表只是表达方式，不要求为每批创建文件；沿原素材、方向或目标文档记录即可。

## 原始输入与素材资格

主系统使用[原始想法模板](../game-design-workflow/templates/idea-template.md)，写入`yanzhou/sources/inbox/YYYY-MM-DD-short-name.md`。探索直接写所属DIR的README，不预建流程目录。记录意图摘要、必要来源、状态Raw Idea / Unqualified和Unknown，按上节裁剪重复字段。

主动使用grill-with-docs，先查允许材料，再按批量澄清约定成组确认关键问题。全部满足以下条件才能晋级：

1. 意图摘要明确，引用的材料及版本可定位。
2. 设计对象或目标GDD章节明确。
3. 玩家情境，或非玩法内容承担的设计功能明确。
4. 玩家行为、可见影响或约束明确。
5. 预期反馈、体验或设计价值明确。
6. 与已有核心、系统、素材的关系明确。
7. 主要未知、下一步验证/决策方法明确。

完整数值和全部制作边界不是入库前提；情绪词、功能名和泛泛愿景不能替代上述字段。信息不足继续Raw；用户选择一个模糊候选也不能跳过资格。通过后按[合格素材模板](../game-design-workflow/templates/qualified-gdd-material-template.md)生成`M-日期-主题.md`并引用输入摘要。主系统放sources/materials，探索放同一DIR。

## 正式GDD

使用[GDD写作要求与模板](../game-design-workflow/templates/gdd-writing-requirements-and-template.md)，明确GDD-0/GDD-1/GDD-2。按本轮阅读授权审查当前规则、决策、问题、已有GDD，以及目标项目正式素材和相关inbox。

- 写到相应章节时给出最相关的素材与Include/Omit/Park建议，不一次倾倒库存。
- 用户采用inbox候选时，先资格确认并晋级，再写正文；模型自行补全的猜测不得写为结论。
- 使用处引用已采用素材的固定版本与定位；已明确采用的来源不重复审查。未读且影响结论的材料列为缺口，不宣称全量审查。
- 新草案放`yanzhou/sources/gdd-drafts/GDD-日期-主题.md`；Accepted规格在design唯一维护。
- 不使用自由散文替代模板，不创建客户端/代码GDD；引擎、类、函数、脚本、API、编程数据结构、CI、Bug与代码进度不入GDD。
- 代码已实现不使Hypothesis自动变Confirmed；GDD写入不自动修改正式采纳范围。

## 提案、评估与采纳

| 阶段 | 前提与输出 |
| --- | --- |
| Proposal | 来源必须是合格素材；使用提案模板写玩家行为、核心反馈、玩法假设、最小验证、参照与未知；不过早展开全套数值 |
| Evaluation | 有合格来源/提案，使用评估模板判断推荐推进、修改后重评、搁置或不推进；说明动作、反馈、核心取舍、最小原型及可验证风险 |
| Draft Change | 以合格来源和提案/评估为据，列拟增删替换文本、影响、理由及来源；未经明确采纳不修改现行核心 |
| Accepted | 用户确认或既有明确采纳授权后，更新design对应权威页、核心摘要（受影响时）与decision-log；同轮提交推送 |

主系统对应sources/proposals、evaluations、draft-changes；探索正式文件直接放所属DIR。跨探索回写须目标项目复审，目标Draft Change在主系统sources/draft-changes。历史已完成的P/E/D可在history/accepted-design-records保留来源，不因归档新增采纳范围。

## 参考产品与理论

顺手提及产品先保存参照；正式拆解写产品案例，横向比较写比较记录。至少说明核心循环、相关机制、玩家价值、可借鉴结构、雷同风险和可验证假设；不因成功产品就复制系统。外部产品拆解正文和公共案例集中写media-analysis-lab/runs；对目标项目的转化、资格和采纳留其sources或方向README并引用报告版本。通用拆解方法写media-analysis-lab/methods，其他通用方法写共享知识。来源可能变化或用户要求最新时联网核实并标注。

理论/文章先登记来源，再用自己的话整理，并回答“它如何改变本项目设计判断”；无法回答时保留学习材料，不直接推进提案。研究不能只堆链接。

## 实现与验证

先确认明确设计来源和规则ID，按目标开发索引进入代码仓库；实现、测试、构建与发布细节留代码仓库。本仓库记录里程碑、范围、证据、阻塞和下一步。偏差、临时替代物单列；试玩观察转研究记录，再决定是否产生设计变更。

没有设计依据先回设计流程；没有执行授权不启动实验。模拟、局部检查与真人体验分别报告，不以历史测试外推新版本，不修改原实验结果。

## 命名与交付

日期用实际YYYY-MM-DD；主题用英文小写、数字和连字符。原始输入无前缀，正式类型用M、GDD、P、E、D、H；共享模板只用[登记清单](../game-design-workflow/templates/README.md)。

每次说明保存位置、Raw/Qualified/GDD/Proposal/Evaluation/Draft Change/Accepted/Parked/Rejected状态及最自然的下一步。保护文件变更必须按[Git规范](github-collaboration.md)提交推送，报告分支和哈希。
