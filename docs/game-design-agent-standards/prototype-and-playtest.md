# 原型与试玩规范

文档 ID：`AGS-PLAY-001`

状态：`Proposed / Phase 4 draft`

版本：`0.1.0`

更新时间：`2026-09-04`

复审日期：`2026-10-04`

## 1. 原型的定义

原型是为了减少一个主要未知而制作的最小可观察版本，不是缩小版成品，也不是展示素材。外观保真度、规则数量和样本规模都由测试目的决定。课程的渐进测试层次是方法参考，不替代本仓库的 S0-S7 阶段（`E-SJ003-P001-001`）。

## 2. 测试合同

每次测试开始前至少记录：

| 字段 | 内容 |
| --- | --- |
| Test ID | `TEST-YYYY-MM-DD-short-name` |
| 主要未知 | 本次只回答什么问题 |
| 目标玩家 | 经验、偏好、招募边界 |
| 版本与范围 | 原型版本、规则、占位内容 |
| 玩家任务 | 可观察动作，不提前暗示方案 |
| 观察字段 | 行为、误解、犹豫、顺序、结果、口头解释 |
| 环境 | 平台、设备、座位/先后手、时长、中断 |
| 成功信号 | 支持保留假设或进入下一阶段的观察 |
| 失败/停止信号 | 必须改向、搁置或停止的观察 |
| 样本边界 | 重复次数、玩家群体、离群值处理 |

## 3. 规则条目

### ADRULE-PLAYTEST-001：测试必须先声明问题和信号

Strength：`SHOULD`

Status：`Proposed`

Trigger：创建原型、安排试玩或宣称“已验证”。

Preconditions：已有目标设计对象和可观察的主要未知；新设计输入已经过素材资格或明确只作为探索性原型，不冒充正式 GDD。

Input：目标设计对象、主要未知、目标玩家、原型版本和测试资源/限制。

MUST：在测试合同中声明一个主要未知、目标玩家、任务、版本、观察字段、成功/失败/停止信号和下一步决策。

MUST NOT：只问“好不好玩”、用功能数量/视觉完成度代替行为证据，或把没有停止信号的试玩标为通过。

Procedure：`写测试合同 -> 自测可运行 -> 外部测试可理解/体验 -> 记录原始行为 -> 对照成功/失败信号 -> 给出阶段门或重测计划`。

Output：测试合同、观察记录和阶段门建议。

Pass criteria：测试结束后可回答“观察到什么、它改变哪个假设、下一步做什么”。

Failure handling：缺关键字段则标 `Unknown`，测试结果只能作为探索性观察；阶段门保持 `Decision state: Pending`、`Gate: N/A` 和 `Pending reason`，不能支撑 `Go`。

Evidence：`E-SJ002-P009-001`、`E-SJ003-P001-001`、`E-SJ003-P002-001`；Wiki `s2-prototype-and-playtest.md`。

Owner/version/review date：原型/测试负责人 / `0.1.0` / `2026-10-04`。

Review trigger：测试目的、目标玩家或阶段门变化。

### ADRULE-PLAYTEST-002：问题信号与玩家方案分开

Strength：`SHOULD`

Status：`Proposed`

Trigger：收集玩家、协作者或设计师的反馈。

Preconditions：测试版本、任务和反馈来源可以定位；非正式评论也可记录，但证据等级必须降低。

Input：测试版本/任务、原始行为或原话、反馈来源和已知上下文。

MUST：分别记录原始观察、玩家解释、玩家提出的改法、设计者竞争解释、下一轮假设和回归范围。

MUST NOT：自动采纳“改成 X”，因建议来自外部而拒绝问题信号，或把设计者偏好写成测试结果。

Procedure：`保留原话/行为 -> 分列观察/解释/建议 -> 提出竞争解释 -> 选择最小改动 -> 写回归问题`。

Output：反馈分类表和至少一个可测试的设计变更。

Pass criteria：读者能看出“哪里不对”与“怎么改”不是同一结论。

Failure handling：根因不清时保留多个解释，标 `Unknown` 并进行定向重测。

Evidence：`E-SJ003-P006-001`、`E-SJ003-P007-001`、`E-SJ003-P028-001`。

Owner/version/review date：测试与设计负责人 / `0.1.0` / `2026-10-04`。

Review trigger：反馈渠道、样本群体或问题分类变化。

### ADRULE-PLAYTEST-003：记录上下文、离群值和替代解释

Strength：`SHOULD`

Status：`Proposed`

Trigger：整理试玩结果、比较玩家群体或准备改变规则。

Preconditions：至少有 Test ID、版本、参与者/样本标识和原始记录；缺失上下文的结果单独标记，不与完整样本合并。

Input：Test ID、版本、参与者/样本标识、测试环境、顺序信息和原始记录。

MUST：记录玩家熟练度、招募方式、版本、环境、先后手/顺序、完成/退出、离群值和可能的环境解释；比较同一群体与不同群体的重复表现。

MUST NOT：用单局、单人、无上下文的结果推出普遍规律，或删除不符合预期的样本。

Procedure：`核对版本/招募/环境 -> 标注顺序和完成状态 -> 识别离群值 -> 比较群体/重复表现 -> 列替代解释 -> 限定结论范围`。

Output：带上下文的观察表、限制和待验证假设。

Pass criteria：结果的适用范围、样本限制和替代解释清楚。

Failure handling：上下文缺失时降低证据等级，不能标 `Confirmed`；必要时重新招募或重测。

Evidence：`E-SJ003-P009-001`、`E-SJ003-P017-001`、`E-SJ003-P018-001`。

Owner/version/review date：研究/测试负责人 / `0.1.0` / `2026-10-04`。

Review trigger：玩家定义、样本策略或测试环境变化。

### ADRULE-PLAYTEST-004：改动要可解释并完成回归

Strength：`SHOULD`

Status：`Proposed`

Trigger：修改费用、时序、卡牌效果、胜负条件、信息显示或其他会改变玩家选择的规则。

Preconditions：已有可复现基线、目标规则/体验和计划修改的变量；没有基线时先建立探索性记录。

Input：基线版本、目标规则/体验、计划修改变量、测试任务和回归范围。

MUST：事前写预期一阶/二阶影响，尽量只改一个主要变量，用同一任务和字段比较前后版本，并列出直接/间接回归范围。

MUST NOT：同一轮同时改变多个不可区分变量后宣称因果明确，或只验证改动目标而跳过不变量和相邻系统。

Procedure：`冻结基线 -> 写变更和预期一/二阶影响 -> 单变量或标组合实验 -> 用同一任务重测 -> 比较结果 -> 执行直接/间接回归`。

Output：变更记录、A/B 或前后版本结果、回归报告和未解释项。

Pass criteria：结果可以与基线比较；无法归因的部分标 `Unknown` 或“组合实验”。

Failure handling：出现严重二阶后果时回退到上一版；阶段门已决定时选择 `Iterate/Park` 并保留失败路径，尚未决定时记录 `Decision state: Pending`、`Gate: N/A` 和 `Pending reason`。

Evidence：`E-SJ003-P010-001`、`E-SJ003-P021-001`、`E-SJ003-P013-001`。

Owner/version/review date：系统设计与测试负责人 / `0.1.0` / `2026-10-04`。

Review trigger：变量无法拆分、基线改变或出现新跨系统影响。

### ADRULE-BALANCE-001：平衡分析必须写上下文

Strength：`SHOULD`

Status：`Proposed`

Trigger：讨论“公平、对称、强势、胜率、先手优势”或卡牌路线平衡。

Preconditions：已明确模式、胜利条件、目标玩家和待比较版本；没有项目平衡目标时只描述观察，不设固定阈值。

Input：模式与胜利条件、目标玩家、比较版本、对局记录和项目平衡目标。

MUST：分别记录起始条件、行动顺序、阵营/核心卡路线、玩家水平、资源/阶段数据、结果和样本；区分“起始对称”与“成功机会/努力回报合理”。

MUST NOT：把相同起手、单局胜负或个人体感直接当作平衡结论；不得使用没有项目目标函数的固定胜率阈值。

Procedure：`定义模式/目标 -> 记录起始条件和顺序 -> 记录路线/阶段/结果/熟练度 -> 检查稳定偏差 -> 提出竞争解释 -> 最小改动并回归`。

Output：对局记录、偏差假设、回归范围和最小补充测试。

Pass criteria：能说明偏差发生在何种玩家、路线、时序或阶段，并有可复验的记录。

Failure handling：上下文不足则保持 `Unknown`，不单独削弱或增强某卡；先补采样和路线记录。

Evidence：`E-SJ003-P011-001`、`E-SJ003-P012-001`、`E-SJ003-P023-001`。

Owner/version/review date：平衡与测试负责人 / `0.1.0` / `2026-10-04`。

Review trigger：胜利条件、模式、玩家群体或数据字段变化。

## 4. 当前项目的最小原型建议（Hypothesis）

用于验证“玩家是否围绕唯一核心卡选择辅助卡组合”：一张核心卡、少量辅助卡、费用池、一次组合结算、一次短战斗和一个共享世界反馈即可。地图、交易、大卡池和真实 AI 行为不属于本次测试范围。成功信号是玩家能完成并解释选择代价、结果和下一步；失败信号是依赖口头提示、把核心卡当普通资源或无法改变路线。

以上只是 `Hypothesis`，不是卡池数量、费用数值或最终流程决策。
