# 三人团队三周垂直切片开发与分工计划

> 文档状态：`Parked / Superseded Pending New Battle GDD`
>
> 原计划周期：15 个工作日，原建议为 2026-08-24 至 2026-09-11；当前不再有效
>
> 团队：`ssn`（总负责人、GDD、策划、代码主力）、`wdr`（代码辅助、地图循环、UI 表现、内容集成）、`lh`（美术、剧情）

> 暂停说明：旧成语组合战斗 GDD 与 `combat-lab` 已于 2026-08-22 归档。本文以下范围、排期、任务、资产和验收仍保留作历史估算，但不授权实现；必须在新战斗 GDD-0/1 与地图接口确认后重写生产计划。

## 1. 计划结论

三周内不以“完成正式游戏”为目标，而是走完一次完整的小型开发周期，交付一个可以独立试玩、收集反馈并支持继续立项判断的离线垂直切片。

原推荐范围是（已失效）：

`选择核心卡 -> 进入固定节点地图 -> 选择相邻节点 -> 获得资源/触发事件/进入战斗 -> 使用核心卡组合与共享战斗能量完成单机 AI 对战 -> 获得结果 -> 继续或撤离 -> 结算本局`

原计划采用“整体循环可玩，内容量极小”的方案。由于其中的战斗、数据、UI 和验收均依赖已归档规则，当前整体状态为 `Parked`，不得按下表启动开发。

### 1.1 三种范围方案

| 方案 | 内容 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 垂直切片 | 固定节点地图 + 事件/资源 + 单机战斗 + 撤离结算 | 能验证地图、战斗和局外目标是否闭环 | 集成压力较高 | **采用** |
| B. 战斗演示 | 只做两张核心卡和八个组合的对战 | 最稳、战斗可打磨更深 | 无法验证当前整体系统主线 | 作为回退方案 |
| C. 系统展示 | 地图、交易、成长、AI 生成均做界面模拟 | 展示面广 | 几乎没有系统能真正可玩 | 不采用 |

## 2. 交付范围

### 2.1 必须实现

| 模块 | 最小内容量 | 验收结果 |
| --- | --- | --- |
| 启动与流程 | 开始、核心卡选择、地图、战斗、结算、重新开始 | 玩家可从头到尾完成一局 |
| 核心卡 | 羊、舟两张人工配置核心卡 | 两张卡的身份和组合差异可见 |
| 辅助卡 | 复用 `combat-lab` 的 20 个辅助卡模板；客户端可按实际 UI 容量裁剪显示 | 能构成并发动首批八个组合 |
| 战斗规则 | 30 血量、攻防阶段、固定 4 点攻防共享能量、单卡 1 费、组合整体定价、攻击/防御组合、原子结算 | 可完成玩家对 AI 的一场战斗，非法行动不污染状态 |
| 地图 | 一张人工配置的 8-12 节点图；入口、资源、事件、战斗、撤离四类节点 | 玩家只能选择相邻节点，并能判断粗略风险/收益 |
| 资源与事件 | 一个抽象资源计数；至少 6 个短事件；奖励、损失、无事三类结果 | 节点结果能改变继续或撤离判断 |
| 撤离与结算 | 主动撤离、战斗失败、完成路线三类结束 | 显示本局路线、资源、战斗与结果摘要 |
| UI 与反馈 | 地图 HUD、卡牌/手牌、血量、能量、组合提示、节点详情、结算页 | 核心状态无需查看控制台即可理解 |
| 美术与叙事 | 统一的低成本视觉样式、核心卡立绘/图标、节点图标、卡面组件、短开场和事件文本 | 无明显临时素材混用，世界设定能解释行动目标 |
| 测试与构建 | 每日可运行构建、关键规则测试、两轮试玩、最终演示包 | 无阻断完整流程的已知缺陷 |

### 2.2 明确不实现

- 实时或异步多人共享世界、账号、服务器、匹配和 PvP。
- 核心卡交易、占领、开发、长期成长和完整经济。
- 真实 AI/算法生成核心卡；本版使用羊、舟两张固定样例。
- 连续 2.5D 大世界、无尽地图和复杂程序化生成；本版使用固定节点图。
- 核心卡收藏库存；一人一张与替换只保留规则说明，不做完整获取系统。
- 存档、云同步、商业化、成就、设置全套、无障碍全套和本地化。
- 完整剧情、过场动画、角色动画、原创音乐和正式音频制作。
- 最终数值平衡；只要求数值可测试、无显著必胜或无法结束问题。

- `ssn` 对范围、规则、构建是否过闸拥有最终决定权。
- `wdr` 对地图循环和 UI 集成结果负责，不只是提交零散代码。

- 每项任务只有一名最终负责人；协作者不能替代负责人验收交付。
- `ssn` 的新增需求必须同时写出要删除或延期的同等工作量，D10 后禁止新增功能。

## 9. 试玩与验收指标

以下数值是三周原型的建议决策阈值，不是已确认的正式设计结论。`ssn` 应在 D1 的 GDD-1 中确认或调整。

| 目标 | 测试方法 | 建议成功信号 | 失败后动作 |
| --- | --- | --- | --- |
| 完整流程可理解 | 5-8 名未参与开发者独立试玩 | 至少 80% 无口头指导完成一次撤离或明确结束 | 优先修流程、提示和结束条件，不加内容 |
| 核心卡身份可理解 | 试玩后让玩家用一句话解释羊/舟差异 | 至少 4/5 能说出主要组合或战术倾向 | 简化组合展示和核心卡说明 |
| 地图选择有理由 | 记录玩家选择节点前说出的判断 | 至少 3/5 出现一次基于风险、收益或撤离的主动取舍 | 调整可见信息或节点结果差异 |
| 共享能量产生攻防取舍 | 观察是否为防御主动保留能量 | 至少 3/5 出现一次有意识的保留或全攻风险选择 | 调整费用、提示或对手威胁可读性 |
| 系统闭环成立 | 追问战斗、资源、路线和撤离是否互相影响 | 多数玩家能指出至少两处相互影响 | 若地图只是点按钮，回退到更聚焦的战斗原型 |
| 稳定性 | 连续完整运行和关键状态测试 | 3 局连续完成；P0/P1 为 0 | 停止表现优化，集中修复阻断与状态污染 |

### 9.1 缺陷优先级

| 等级 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 | 无法启动、数据损坏、无法继续或必现崩溃 | 立即停止其他工作，全员协助修复 |
| P1 | 核心规则错误、流程无法完成、状态污染、主要 UI 不可操作 | 当日修复，RC 不允许遗留 |
| P2 | 明显误导、频繁体验问题、重要反馈缺失 | D13 前按收益排序处理 |
| P3 | 轻微表现、低频边界和非关键优化 | 记录到后续，不阻止交付 |

## 13. D15 决策规则

- `Go`：完整流程、核心卡身份和至少一种地图/战斗取舍均达到成功信号，且没有结构性技术阻塞。进入 4-6 周制作验证，优先扩充内容和验证重复游玩。
- `Iterate`：流程可玩但关键体验信号不足。只选择一个最大失败点再做 1-2 周验证，不直接扩内容。
- `Stop/Pivot`：玩家无法理解或不在意核心卡与战斗的关系，地图与战斗长期割裂，且问题不能通过小调整解决。保留[归档 `combat-lab`](../../archive/2026-08-22-idiom-combat-system/combat-lab/README.md)和试玩证据，回到提案/评估阶段。
