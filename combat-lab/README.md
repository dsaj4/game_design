# 成语组合战斗独立测试系统

`combat-lab/` 是与正式游戏构思链隔离的确定性规则原型。它用于检验“低数值辅助卡 + 字段匹配 + 核心卡成语组合”是否可计算、可构筑和可平衡，不代表规则已经被正式采纳。

## 第一批原型边界

- 双方基础血量值暂定为 30。
- 核心卡只包含 4 个公开成语组合，不包含常驻被动或独立主动能力。
- 每张核心卡至少包含 1 个攻击组合和 1 个防御组合。
- 辅助卡只有一个属性和一个数值为 1 的基础效果，不产生场面。
- `attack` 对应 1 点伤害，`defense` 对应 1 点护盾，`dispatch` 对应抽 1 张，`disrupt` 对应弃 1 张。
- 属性决定基础效果；字段只用于组合匹配。一张辅助卡可以有多个字段。
- 第一批卡组各 20 张，每张辅助卡模板放入 2 张。
- 费用、完整抽牌回合、电脑出牌策略和批量胜率模拟尚未加入。

## 组合匹配条件

字段条件被实现为不考虑顺序的多重集合，但参与牌必须是不同卡牌实例：

- `羊 x3` 必须选择三张不同的牌。
- 一张同时包含 `羊`、`牢` 的牌，在同一次组合中只能填一个字段槽位。
- 选择的牌数必须恰好等于组合要求的字段槽位数，不能加入无关牌。
- 同一张牌在一个回合内只能参与一次组合；当前引擎通过结算后进入弃牌区保证这一点。
- 攻击组合只能从攻击方手牌发动；防御组合只能从防守方提前公开的 `prepared` 防御准备区发动。
- 一次 `resolve_exchange` 只允许一个攻击组合和至多一个防御组合。

## 原子结算顺序

一次攻防交换按固定顺序执行：

1. 验证参与牌属于正确区域并满足字段条件。
2. 移动攻击组合参与牌到弃牌区。
3. 按玩家选择顺序结算参与牌的基础效果。
4. 按数据表顺序结算攻击组合效果。
5. 若防守方发动组合，以相同步骤结算准备区中的防御牌和组合效果。
6. 先从攻击伤害中扣除 `block`，再由护盾吸收剩余伤害，最后扣除血量值。
7. 防御准备区中未使用的牌返回手牌。

所有步骤在状态副本上完成；任何条件不合法时，整次交换回滚，不消耗牌或血量。

`pay_health` 直接扣除自身血量值、无视护盾，并且支付后必须至少剩余 1 点。回复不能超过 30 点血量上限。

第一版沿用“所有辅助卡基础效果都会结算”的已确认原则。因此攻击属性牌参与防御组合时会反击对手；防御属性牌参与攻击组合时会先给自己增加护盾。这是显式测试假设，后续可以根据试玩结果修改。

## 持久组合

- 持久组合消耗参与的辅助卡，场上只保留结构化状态，不保留牌本身。
- 每位玩家最多拥有 3 个持久状态。
- 第一批持久状态在玩家自己的回合开始时触发，共触发 2 次。
- 同名状态不叠加；再次生成时刷新为 2 次触发，不占新槽位。
- 第一批持久效果只允许回复或增加护盾，禁止递归生成状态或额外行动。

## 第一批核心卡

以下数值只是便于比较的 `v0` 测试基准。辅助卡基础效果需要另行加到组合收益中。

| 核心卡 | 组合 | 分类 | 字段条件 | 组合效果 |
| --- | --- | --- | --- | --- |
| 羊 | 三羊开泰 | 持久防御 | 羊 x3 | 抵挡 2；随后两个己方回合开始时各获得 1 护盾 |
| 羊 | 亡羊补牢 | 瞬时防御 | 羊 x2 + 牢 x1 | 支付 2 血量，获得 6 护盾 |
| 羊 | 羊入虎口 | 瞬时攻击 | 羊 x1 + 虎 x1 | 造成 4 伤害 |
| 羊 | 顺手牵羊 | 瞬时攻击 | 羊 x1 + 手 x1 | 造成 2 伤害，回复 2 血量 |
| 舟 | 破釜沉舟 | 瞬时攻击 | 釜 x1 + 舟 x1 | 支付 3 血量，造成 7 伤害 |
| 舟 | 顺水推舟 | 瞬时防御 | 水 x1 + 舟 x1 | 抵挡 2，回复 2 血量 |
| 舟 | 同舟共济 | 持久防御 | 舟 x1 | 随后两个己方回合开始时各获得 1 护盾 |
| 舟 | 逆水行舟 | 瞬时攻击 | 水 x1 + 舟 x1 | 造成 2 伤害，回复 2 血量 |

`同舟共济` 只要求一张牌，因此组合额外价值暂定为延迟获得 2 点护盾，低于二牌或三牌组合。`顺水推舟` 与 `逆水行舟` 使用相同字段，但分别限定在防御和攻击阶段，测试同一组字段在不同回合计划中的灵活价值。

## 数据和代码

- `data/auxiliary_cards.json`：20 张辅助卡模板及其属性、字段、基础效果。
- `data/core_cards.json`：两张核心卡和 8 个结构化组合。
- `data/decks.json`：两套 20 张测试卡组。
- `combat_lab/matcher.py`：字段多重集合匹配。
- `combat_lab/engine.py`：原子攻防结算和持久状态触发。
- `tests/`：数据约束、字段匹配和结算测试。

## 运行

在本目录执行：

```powershell
python -m combat_lab validate
python -m combat_lab show
python -m combat_lab analyze
python -m pytest -q
```

`analyze` 会精确枚举 20 张卡组的全部四张起手和五张可见牌组合，报告每个成语以及任意攻击/防御组合的可达率。它只测字段供给，不把费用、出牌策略或此前回合已经消耗的牌计入结果。

## v0 字段可达率基线

当前两套卡组用于覆盖所有规则路径，字段密度有意偏高，不能视为平衡结果：

| 卡组 | 可见牌 | 任意组合 | 任意攻击 | 任意防御 |
| --- | ---: | ---: | ---: | ---: |
| 羊 v0 | 4 | 99.7% | 89.5% | 82.6% |
| 羊 v0 | 5 | 100.0% | 94.9% | 96.3% |
| 舟 v0 | 4 | 99.7% | 95.4% | 99.7% |
| 舟 v0 | 5 | 100.0% | 98.3% | 100.0% |

单组合四张起手可达率为：三羊开泰 65.7%、亡羊补牢 54.3%、羊入虎口 62.0%、顺手牵羊 62.0%；破釜沉舟 62.0%、顺水推舟 79.0%、同舟共济 99.7%、逆水行舟 79.0%。

这表明当前 `v0` 更适合验证结算与组合选择，不适合检验“凑成组合”的稀缺感。下一批卡组应在不改变八个组合定义的情况下减少核心字段密度，并比较组合可达率、无组合手牌比例与基础效果损失。
