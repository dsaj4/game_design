# 开发阶段与启动条件

2026-10-18 · DevelopmentPlan。用户已明确**先完善主系统，再开始下一实现**。本页只维护阶段定义、依赖和下一步；实际包与证据由[开发状态](README.md)统一维护，不按批次继续叠加“当前”。

## 本轮顺序

1. 收束规范、当前状态、工作台入口和开发解释；保留原件及失败证据。
2. 设计对接先处理[FB-Q01主动调度](../governance/questions.md#开发前先看)，连同积累／兑现取舍明确首批玩家行为。
3. 选择2D启动范围，完成对应内容及展示合同；冻结可实现、可检查的输入。
4. 再启动2D工程任务。是否复用Godot规则底座、如何隔离表现与旧包，在实现仓库按实际依赖决定；本轮不预建双实现或通用Adapter。

用户已在[本轮Q2](../sources/inbox/2026-10-18-development-system-review.md#本轮批量澄清)确认“先闭合首场核心玩法”：主动调度、积累与兑现、首批内容和一场完整战斗输入先闭合。路线、商店和扩展系统随后按需补齐；不要求先完成全部主系统。若首场实际用了某项扩展，其必要规则仍须先明确。

## 阶段地图

沿原P0—P5身份，不重新编号。阶段可有局部成果；满足本阶段全部范围和退出条件才标完成，不能将各项百分比相加。

| 阶段 | 对玩家意味着什么 | 退出条件 | 目前证据的解释 |
| --- | --- | --- | --- |
| P0 工程可交接 | 能打开程序，得到可重复的版本 | 固定输入、恢复工程、独立包、可复现入口与接手记录 | 既有Godot有独立包与复制检查；实际断网／独立人员接手等未验保留 |
| P1 规则可信 | 同样操作产生同样的合法结果 | 对应范围的生产、支付、队列、敌情、终局与保存有预期和检查 | 已有EX案例规则底座；未覆盖全部GDD与未来内容 |
| P2 能看懂并操作 | 看出当前情况，操作可达，反馈指向正确对象 | 信息完整、公开安全、真实状态、输入和停点一致；关键状态在目标尺寸核对 | 3D有多批限定证据及新UI候选；用户最终接受和理解未成立 |
| P3 一场能完整玩完 | 开始、战斗、胜败、恢复、重试连成一体 | 同一固定包完成全链及失败路径；保存一致；表现与规则没有回归 | 0.4旧界面有完整单战证据；不能给B13或新2D自动继承整项通过 |
| P4 一局有构筑与成长 | 在战斗之间取得、组合、取舍并走到本局终点 | 真实有限库存、路线、奖励、商店／休整、跨战与节点恢复闭合 | 尚未启动；真实内容、取得链、价格与路线范围仍缺输入 |
| P5 内容与交付可靠 | 多次游玩仍有选择，目标设备上能稳定交付 | 选定内容、体验观察、性能、可读性、存档兼容、来源及构建证据齐备 | 尚未达到；长期性能、真人理解与整体平衡仍有缺口 |

P3是完整单战Demo的目标，P4才涉及最小局内循环。首场通过不等于发行完成，也不能用一张完成的效果图跳过P1、P3或P4。见[开发解释](development-guide.md)。

## 2D开工前检查

| 要冻结的输入 | 主责与唯一入口 | 未满足时 |
| --- | --- | --- |
| 玩家主要在判断、调整和放弃什么 | 玩法设计；FB-Q01／02与正式来源链 | 留在主系统完善，不用按钮或动画替代设计答案 |
| 首批内容、初态、胜败与失败情境 | 内容设计；案例与内容合同 | 不凭EX-002推导其他构筑或整局默认 |
| 2D操作宿主与信息承载 | 设计对接；PRE2D-Q01及CORE-063的限定变更 | 不把二维实现声明为现行3D合同已通过 |
| 已确认行为的沿用／替代清单 | rules与Draft Change；CORE-060—062等 | 只重开有具体新需求的条款，已确认选项不重问 |
| 目标演示范围和退出条件 | 本页与本轮合同，受用户Q2选择约束 | 不自动承诺路线、商店、复杂状态或全部内容 |
| 工程与资产复用结论 | 对应代码仓库、AS／DM登记 | 先做静态依赖与来源核对，需运行验证时明确任务范围 |

此表不是要求所有系统在开工前全部完成。每项必须对选定范围有唯一答案，范围外问题明确延期；开工记录将设计提交、代码起点、资产版本和验收场景绑定。

## 每轮怎样推进

采用[制作小循环](iteration-spec.md)。一个循环只解决一项可观察变化，优先让一个代表状态完成“设计→目标情境核对”，通过后再扩量。每轮交接说明：完成的玩家能力、所在阶段、实际检查、剩余依赖和下一项。

技术问题与Bug留实现仓库；设计取舍进入questions并沿DOC-024暂停；工作台展示来源、产物和审阅入口，不保存第二套权威状态。
