## 2. 一项开发任务怎样开始与结束

开工前写清：目标玩家行为、引用规则／UI状态、设计提交、代码起点、资产版本、范围内外、验收场景与依赖。任务以可运行行为或可验证产物拆分，例如“第7拍切用途且旧批次不变”，避免“完成战斗系统”式大任务。

完成时至少提供：代码提交、可复现启动／构建入口、实际检查结果、使用的资产版本、已知偏差与未测范围。修复失败须复跑相关检查；不要为交差只更新截图或删除失败用例。未运行项继续NotRun；已通过的局部检查不写成全游戏完成。

只有本阶段范围验收通过、无影响该范围的已知阻断缺陷，阶段才完成。调整范围需说明剩余内容去哪一阶段，不以临时隐藏功能冒充实现完成。

## 3. 逻辑与表现必须可以独立核对

- 相同初态、内容版本及有效操作序列应得到同样的事件顺序和结果。逻辑按TL-11推进，帧率、镜头、动画时长和播放倍速不改变结算；随机内容开始使用时固定并保存随机状态。
- 游戏状态只有一个权威结果。界面提交合法意图并显示结果，不能同时在动画回调和规则流程中各扣一次血或费用。
- 当前批次、未来选择、实际入队、预计生效、历史结果分别表示。界面隐藏信息的检查与后台完整模拟分开，未揭示敌牌不能通过摆位／提示泄露到期拍或量值。
- 素材实例与游戏对象身份分开。换模型、换材质或缩放视窗不改变铭文库存、法器数量、行动队列和配方。
- 调试工具可以指定初态、单步和查看完整账目，但必须与玩家界面区分；调试窗口的全知数据、重置和跳拍不可进入正常玩家操作。

这是实现可验收的约束，不指定代码框架。引擎、语言、渲染管线、保存格式及资源导入方式在选型后由代码仓库ADR记录选择、替代方案、代价和验证依据；不为本轮管理规划预建技术架构树。

## 4. 内容与失败处理

所有运行内容先做完整性检查：稳定身份、合法配方、D、张数、目标、费用、步骤、失败分支和需要的状态字段。明示零材料有效，缺材料字段不能当0；没有定义的材料、契合或疲劳不靠程序猜值。

错误输入应被拒绝并定位到内容和字段；可预期的缺料、缺位、费用不足、无目标与打断按游戏规则处理并显示原因，不能混作崩溃或静默丢数据。终局停止后续事件，结果只提交一次。

保存沿TL-19／36：最近结清事件、已提交操作、队列、批次、敌情、费用及领取状态可恢复。保存失败保留原结果并停止后续不可逆提交；读档失败不覆盖原文件或悄悄新开局。保存版本升级、迁移和回退方案属于代码仓库技术工作，升级前保留可恢复输入。

## 5. 资产接入

**现成资源优先（2026-10-15 用户明确要求）**：每项美术/表现开发先查[当前资产入口](asset-readiness.md)、[统一目录](../../docs/registry/demo-assets.md)与[工程资源接手](E:/Project/yanzhou-godot/docs/development-handoff.md#资源选择与恢复)。按「当前已验证运行资源 → 本项目固定源库 → 已核参考候选 → 必要时另找现成来源 → 确有缺口才新建/生成」选择；开工记录目标、源ID/版本、适配内容。能通过现成模型、贴图、分层、切片和动作的必要调整实现时，不重复制作；选择新建时注明查过的候选和具体不适用原因。已使用的固定资源不因出现新候选自动替换，现成资源不能反向新增玩法。依据见[用户原话](../sources/inbox/2026-10-15-demoncards-asset-integration.md#同日追加后续优先使用现成资源)。

源工程、导出文件、运行时加工版与检查截图分别保存。原AS固定版本只读；烘焙、减面、拆分、材质修正、碰撞和动画另存派生版，记录源ID、源哈希及使用者。源码仓库按实际需要带入运行依赖，不将本机绝对路径、临时服务器或临时附件作为运行依赖。

导入后检查比例、朝向、相机、法线／背面、纹理、透明／透射、灯光、点击区域和重导入后的保留行为。用运行环境截图对照源渲染；允许的差异须列明，不把GLB可解析当视觉一致或性能通过。

大二进制的版本保管方式在选型阶段明确，完成一次从固定清单恢复工程的演练。音频、字体、特效或运行时卡面尚缺的，用明确占位保证功能开发；占位清单由实现仓库维护，在对应验收前替换。资产许可和分发条件沿原记录，内部接入与对外发布分别处理。

## 6. 检查层次与验收记录

| 检查 | 必须证明 | 不能替代 |
| --- | --- | --- |
| 文档／内容检查 | 链接、字段、合法配置、版本及输入完整 | 运行正确性 |
| 规则自动检查 | 指定初态和操作下的步骤、支付、队列、终局结果 | UI可操作与体验 |
| 引擎集成检查 | 真按钮／键盘、选择、显示、保存恢复与实际数据绑定 | 玩家能理解 |
| 构建检查 | 脱离编辑器，清洁目录启动、离线运行、保存及退出 | 其他机器性能 |
| 性能／可读性检查 | 指定机器、分辨率、质量档和场景的测量与观察 | 所有硬件表现 |
| 玩家体验检查 | 玩家预测、选择理由和误读的真实观察 | 全局平衡结论 |

每份运行证据记录日期、机器、引擎／包版本、代码提交、设计及内容版本、输入、预期、实际、通过／失败／未跑、日志或截图。先验证关键路径和高风险失败，新增变化只扩大相关检查；不写镜像实现的无意义测试。

非功能目标在阶段P0冻结：目标Windows版本和硬件、主／最低分辨率、目标帧率、加载和保存等待预算、内存／包体观察指标。建议先以1920×1080、60fps作为评估工作目标，并检查1366×768；这是计划建议，不是已经测得的最低配置。字体缩放、键盘、静音与减动效沿现行可达性合同。

### 制作与验证经验

以下保留[旧开发复盘](../history/README.md#治理历史)中仍适用的失败经验，具体失败数据与恢复办法留原固定记录及代码仓库。

- 先让一个代表对象走完文字、示意、源件和真实运行，再批量扩量；用同一对象／状态／尺寸对照，源件、材质、引擎表现分层验收，技术项通过不代表用户接受。
- 源码HEAD、执行包、构建与截图相位分别固定；完工事件不等于拍末，曲线文件存在不证明运行调用。示意、DOM桩、手动帧／时间或Viewport注入不证明连续操作、OS输入或声音体验。
- 在问题发生层修复：运行过曝／透明／色差先查灯光、导出与派生材质；碰撞须贴可见几何，不穿透或换点击点规避。二维皮肤不替代三维几何，视觉余留不延长队列占用。
- 字体、文案和视口变化后重查换行、分页、遮挡与关闭入口；中心可点不代表边缘读数可读。动态名称／数值独立渲染，不烘入图片；效果图和导出成功不保证规则数值或引擎结果正确。
- 模拟只支持其模型：付得起不代表局内能取得，胜利子集不能掩盖失败，枚举胜率不等于玩家胜率；既定指标达标仍须检查普通战斗零损耗等目标遗漏。旧临时规则不恢复为当前待办。
- 会话closed、阶段产物、验收通过分别报告；后续运行结果不回填早期HTML或听感检查，性能尖峰失败和中断长测各保留原状态。

## 7. 变更与协作

每次改动聚焦一个可解释结果。开工检查Git状态，使用任务分支，只暂存本人任务文件；不覆盖用户修改，不强推。设计仓库保护文档按[Git规范](../../docs/github-collaboration.md)同轮提交推送。

日常可逆实现由开发者自行推进。改变已采纳玩法时按原来源／评估／Draft Change流程；重大难回退技术决定写ADR后形成具体评审结果。用户已有明确授权不重复询问。引擎试做的可复用部分经检查后进入唯一正式工程；不长期维护两套战斗实现。

阶段结果回填[开发入口](README.md)；规则验收定义仍在[validation](../design/validation.md)，实现证据留报告，不篡改历史失败和NotRun。

## 8. 设计裁决闸门

2026-10-11新增，依据用户原话：“开发过程中如果遇到需要裁决的设计问题则暂停，交由专门的设计对接agent进行一轮解决后继续。”登记为 G002-DOC-024。此规则在言咒开发中优先于“先推进不受缺口影响的实现”的一般安排。

1. **识别与暂停。** 当规则相互冲突、关键行为／参数未定义、两个以上相容方案需要取舍，或必须改变已采纳玩法才能继续时，总控将当前开发批次标为“暂停—待设计裁决”，停止新的实现、集成和构建／测试派单；正在执行的工作在可保全边界停下，保留已有改动和证据。只读核对、证据保全、记录与设计对接可以继续，不能以临时值或开发者猜测绕过暂停。
2. **专人接手。** 总控将问题ID、触发场景、已确认决定、受阻DQ任务、固定材料、候选及影响交给一名专门的设计对接agent，按[AGC-1](../governance/agent-collaboration.md)分配独占路径。该agent先查允许的现行资料，再形成可评审方案；需要用户裁决时由该agent按项目批量澄清给出推荐及影响，开发agent不自行选玩法。
3. **一轮回传。** 回传逐项说明：依据现行规则已解决／用户已确认／仍待裁决／范围外延期，附适用边界、拟改内容、验收预期及状态。模型推荐、代理意见一致或一轮对话结束均不等于解决；仍有阻塞则继续暂停。问题仍只登记在questions，候选、资格及采纳沿原来源流程，不另建问题数据库。
4. **复核后恢复。** 总控确认本批阻塞全部解决或被明确排除出本批范围，必要的合格来源、Draft Change、用户采纳及权威文档已落地，接口／验收预期无歧义，再记录恢复依据、版本与任务ID并重新派单。不因已回答部分问题就自动恢复整批；不重复确认已有明确决定。
5. **区分工程缺口。** 规则已有唯一答案而代码尚未实现、实现偏离规则、构建失败或证据不齐，属于工程问题，本身不触发设计裁决；如修复必须作新设计取舍，才进入本闸门。已因其他设计问题暂停的批次中，这些修复也留待恢复后执行。临时限定恢复某个独立开发任务须有用户明确指示，并记录范围。

本规则不自动授权新玩法、实验、后台常驻或对外发布。专门设计对接职责与开发总控职责分开，统一提交与最终恢复决定仍由总控执行。

## 9. 每项重点交互的四阶段制作

2026-10-12 · G002-DOC-025；2026-10-18按G002-DOC-026补充复用与裁剪。原用户要求每个重点交互依次经过文字结构、HTML示意、美术效果、真实实现；本轮明确小修改复用已确认产物，只补变化和对照，工具调研按缺口触发。新重点交互的四类证据及依赖顺序继续保留，不新增逐页审批。

| 阶段 | 具体产物 | 进入下一阶段的核对 |
| --- | --- | --- |
| 文字结构设计 | 玩家目的、操作宿主、进入／退出、信息、状态及操作／事件顺序；包含暂停、单步、回看、载入、异常与键盘 | 规则及后端事实对应明确；已确认与制作建议分开，真正设计取舍先按第8节闭合 |
| HTML示意图 | 同一交互的可查看／可操作结构稿，展示关键状态、空间与点击路径 | 路径能走通、必需信息齐全；明确只是示意，不冒充引擎真实实现 |
| 带美术效果示意图 | 同结构的镜头、布局、姿态、材质、读数与关键动作帧 | 与文字和HTML逐项一致，图形表达对象和状态，不能在美术环节更改功能 |
| 真实实现 | 在本轮选定的正式实现工程接入真实规则、输入、资产和反馈，提供对应运行证据 | 对照前三阶段检查空间、操作、反馈与规则结果；规则正确、工程可运行、视觉／交互一致、用户接受及真人体验分别记录 |

每个新重点交互仍由专门设计agent保持设计责任连续，真实实现后回到设计复核，再由总控集成；沿已确认交互的小修可复用既有设计产物，不自动增加会话。每阶段在所属任务记录留下可查看产物、复用依据与复核；旧3D任务继续引用[原DQ身份](https://github.com/dsaj4/game_design/blob/f21058a54b096e0d6ad2b3b559e352b67596c239/yanzhou/development/demo-quality-taskboard.html)，新方向不直接复制旧完成状态。一张全局效果图不能代替每项关键状态；旧HUD加动画不能作为既有3D主交互验收。

代表制作链优先覆盖法器产牌→卡片入列→合法揭示／使用→目标反馈→离场及点击近观，再扩用途／数量、读数、播放／单步／速度、回看、抽屉与系统页。首条链完成不表示其余已完成。3D沿CORE-063真实物件合同；2D须先完成新方向展示合同。可逆造型／排版沿已有授权推进，改变玩家可见规则仍触发第8节。
