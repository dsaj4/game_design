## 先讲清楚：我们正在做什么

“《言咒》是一款让玩家编排自动战斗的游戏。你用铭文装配法器，法器在每轮五个生产拍里产卡到手。你切换查看可战斗与不可战斗两组手牌，选择可战斗牌免费放到尚未开始的列。手牌没有硬上限；确认后双方逐列结算，每个非末列结清后可再布置更右列，可回收牌也能回手后再次打出；敌人先铺暗牌，延时产生的下轮后续牌会完整公开。

“新首场的起始配置、五位敌表和完整操作路线已经选定。接下来把生产、手动布牌、列间确认与两组持牌做成清楚的二维界面。玩家是否能理解这些选择、布牌、回收再用与合成是否形成有意义的取舍、普通与兑现是否都有价值，还要留到实际实现与体验中检验。”

| 现在有什么 | 怎样理解它 | 下一处缺口 |
| --- | --- | --- |
| GDD 3.1 / GDD-0；唯一核心＋按需细则 | 已有主循环和具体规则；3.1是版本，GDD-0是文档成熟度，两者都不是完成百分比 | 全部系统、发行内容和全局平衡尚未闭合 |
| EX-004完整首场、EX-003局部案例；EX-001／002旧回归 | 新首场初态、敌表、胜败与恢复已有纸面预期，旧案例保留 | 实现及体验未验证，不能继承旧运行证据 |
| 旧Godot 0.4单战底座与B13三维预览 | 有各自固定范围的实现和检查证据 | CORE-067已有独立限定证据；CORE-068背包供料尚未实现验收，旧包不能证明新规则已通过 |
| 首场完善与同一游戏2D方向已确认 | 有下一步设计顺序 | FB-Q01主动调度、FB-Q02积累兑现、内容取得链及PRE2D-Q01展示合同仍待处理；新2D工程尚未建立 |
| 四个任务设计包及对话审阅规范 | 已把完整首场、回合手牌、战前用途与待料、打断重开整理成可交接输入 | 尚未完成真实开发接手或玩家理解验证；任务包不是自动化系统 |

当前规则中，用途与背包布局战前固定；材料在生产观察窗锁解以保护手牌免于自动补料，标记可在生产观察与最终整理锁解。待料至多下一批，自动默认开启且可关闭；生产暂停收尾当前拍；结算暂停收尾当前列，非末列结清后可布置尚未开始的己方列，但不能改用途、供料或锁解；最终整理确认后才开始结算。单法器启停、按保留层数持续增伤和新的二维操作宿主仍不能当作已有功能。依据：[核心](../design/GDD.md)、[基准](../design/baseline.md)、[当前问题](../governance/questions.md#开发前先看)。

## 人和agent怎样分工

“你负责决定想要的玩家选择，以及愿意保留哪些代价。agent负责把这件事讲具体，核对规则、指出影响、完成已授权工作，并把证据放回正确位置。”

| 责任 | 具体工作 |
| --- | --- |
| 人 | 表达目标，判断选择、成本、时机、胜负、信息公开的取舍；明确采纳需要改变的行为 |
| 设计agent | 查已有答案，用故事和反例讲清方案；形成必要来源与变更，维护权威设计及任务包 |
| 开发agent | 实现已经明确的行为，检查真实结果，记录偏差；遇到设计取舍交回设计处理 |
| 协调与审查 | 固定版本和范围、分配文件、核查交付、汇总未决；独立审查须区分于作者自评 |

这是责任划分，小任务可以由一个agent顺序承担；不意味着每项任务都要开多个会话。确需分工时沿[AGC-1](../governance/agent-collaboration.md)，不重叠写同一文件。

## 情景一：我有个想法，先帮我想清楚

**你：**“我希望前期能调控法器，后期又能像工厂一样连续运行。”

**agent：**“这是要改善玩家选择。当前零材料护符不能靠停供停止生产，调整优先级也不保证能改变攻防节奏。我们先比较‘控制未来批次启停’和‘用有限材料调供给’能带来哪些不同操作。两者都是候选。”

接下来用同一局面比较：快受伤时怎样转防、想兑现时牺牲什么、敌人打断前还能改什么。先从允许材料中找已有答案，再把必须由你选择的问题按主题成组讲清；每项给推荐及影响，未答仍保持未知。

如果是新方向，摘要和候选放所属DIR的README；直接完善主系统则放相关inbox。只有对象、场景、可见行为、价值、与现有设计关系和主要未知说清，才进入合格素材及必要提案／评估。**“这个方向不错”不自动等于某套具体规则已采纳。**

本例保留CORE-065之前的讨论方式，不是当前优先候选。现行CORE-067已采用免费手动布牌与列间回收再用，选择价值仍待验证；启停或有限材料仍未因本稿得到采纳。

## 情景二：我决定改规则，怎样让所有地方一致

**你：**“暂停时把这一拍该处理的都处理完，动画也播完，再停。”

**agent应先讲清后果：**“打断揭示也使用同一规则。敌牌揭示后，本拍会继续结算并完成合法开工，你在暂停后作的调整影响后续拍。终局仍停止余下结算；异常载入也不会自动补跑。”

这是先前已采纳的CORE-064历史示例；当前首场由CORE-065进一步区分生产拍与结算列，不能继续照旧拍序实现。这个例子展示了正式修改的完整路径：

1. 保存意图和决定摘要，查已有来源与规则。
2. 把受影响行为准备成可审变更：手动暂停、自动暂停、失焦、详情、单步、退出与恢复。
3. 对新的取舍取得明确采纳；已有明确决定直接沿用。
4. 更新权威规则、必要核心说明、验收预期及受影响任务包，记录替代关系。
5. 固定提交后，把实现任务交给开发；设计更新本身不代表程序已经改变。

如果包还没同步，就标为待同步，停止用于新实现。版本在本轮登记一次，引用定位到具体章节，不重新建立一套来源审查报告。来源：[CORE-064](../sources/draft-changes/D-2026-10-23-beat-end-pause.md)、[轻量记录](../../docs/design-workflow.md#言咒轻量记录)。

## 情景三：规则已定，怎样交给开发

**你：**“实现下一批待料的调整，当前加工不要跟着变化。”

**agent：**“本轮交付是：玩家调整待料后，能分辨当前加工、下一批待料和实际生效。我们先固定设计提交与代码起点，读取用途包，再按实际改动补排程、交互或保存章节。”

现有[用途包](task-packs/future-purpose.md)按CORE-068解释：用途战前固定；生产观察窗只改尚未吸收的下一批材料，不影响当前加工。自动补料只补可凑齐配方的空缺，不替换已放料，最早下一拍吸收；最终整理不能编辑生产待料。尚未开始列的己方牌可免费调序：在EX-003的4层局面中，普通先打可先攒到5层，让后面的兑现付足费用。两种操作都免费，但对象和生效时点不同；兑现卡效的5层费用仍到实际步骤才支付。

开发需要带走的是一组能判断对错的要求：

| 局面／操作 | 应检查什么 |
| --- | --- |
| 观察窗中换待料 | 旧批次不变，新投入最早下一生产拍吸收；战中改用途拒绝 |
| 末拍收尾后请求供料编辑 | 已进入最终整理则拒绝，下一生产观察窗重新提交；不暗存为下轮操作 |
| 兑现时费用不足或目标失效 | 按内容声明回退或空放；不能为了界面顺畅临时改规则 |
| 中途保存恢复 | 当前批次、待料归属／最早拍、自动开关与合法已提交输入保留；不重复扣费、发牌或重排列位 |

正式任务还要带上固定内容、范围内外、必要失败情境及完成条件。EX-002所继承的EX-001输入另有固定版本，不能把所有“最新文件”混成一包。

纯规则修复可以直接形成预期、修复、运行检查；没有视觉变化时不要求重画HTML。新重点交互则按**文字／状态→可操作HTML→代表效果→真实实现**推进；小视觉改动复用已确认产物，只补差异和真实宿主对照。实现证据留代码仓库，本仓库只更新能力、范围与入口。两种路径均沿[小循环](iteration-spec.md)及[开发规范](development-standard.md)。

## 情景四：开发卡住了，谁来决定

**开发agent：**“规则说当前批次不能撤销，但这个按钮若要立即停机就得取消当前批次。”

这会改变玩家承诺和损失，属于设计取舍。本批进入“暂停—待设计裁决”，保全已有工作，停止新实现、集成及构建／测试派单；只读核对和设计对接继续。专门设计对接查已有答案，再准备明确候选和后果。

你不需要回答“代码用哪种类结构”，需要回答的是“是否允许撤回已经承诺的批次，代价是什么”。只有阻塞已解决或被明确排除、必要采纳已落地、任务输入更新后，协调者才恢复本批。agent完成一轮讨论不代表可以自动恢复。

相反，若规则已明确“解锁后仍等合法消费时点”，代码却立即扣费，这是工程偏差，直接按规则修复。若本批已经因别的设计问题暂停，这项修复也等待恢复，除非你明确允许限定任务继续。依据：[设计裁决闸门](development-standard.md#8-设计裁决闸门)。

## 情景五：我不想读细则，带我审一次变更

**agent：**“先看一个具体局面。你有9层施法次数，锁住5层，所以当前能花4层。下面沿EX-004的实际卡效、合法目标、无额外冻结或待释放量，并假定攻击后未终局。”

| 你的选择 | 兑现时会怎样 | 你实际保留或付出的东西 |
| --- | --- | --- |
| 保持锁5层 | 可消费4，不够5；回退为6伤，成功后加1层 | 没花兑现费，实有变10、仍锁5；错过强化伤害 |
| 在本轮确认结算前的合法窗口解锁1层 | 可消费变5；轮到兑现时付5，打18，再加1 | 最后实有5、锁4；解锁本身不提前出牌或扣费 |

**你：**“够直观。”

这表示这个后果已被解释清楚。若你改说“我希望解锁就立刻兑现”，就产生了新的时机和队列取舍，需要回设计流程；不能直接当作一个小按钮修复。

一轮审阅按**定位→正常故事→反例与代价→一张图→收口**进行。人判断选择、成本、时机、胜负和信息公开；agent核对公式推导、重复项、版本与引用。单一情景不能代表全部已审完。

  B -->|保持锁定| C["到兑现时：不足5，回退6伤"]
  B -->|解锁| D["可消费5，等待合法兑现时点"]

**审代码交付时再加一层对照：**固定设计、代码和包，展示“预期→实际→证据”。真实运行、HTML示意和生成效果图分开标明；没有运行就记NotRun。本次只核对设计文字，不能据此宣布实现或玩家体验通过。

你的反馈尽量落在“哪一版、哪个场景、哪个后果”：例如“第3轮第1列打断施法护符后，先前已产入手的牌应该保留，当前包却把它删了”。agent先判断是实现偏差还是你希望改变规则，意见和复核写回同一轮，只留摘要。依据：[场景审阅](design-review.md)、[打断包](task-packs/interruption-restart.md)。

## 情景六：在工作台里看进度和产物

“打开工作台后，先找当前这一轮，再看一个主审阅入口和2—3个代表状态。要判断的不是有多少张图，而是哪项玩家能力已经成立。”

按[本机使用说明](workspace.md)，可从`E:/Project/yanzhou-workspace/Start Yanzhou Workspace.cmd`启动。项目卡组织当前、循环、审阅、资产、地图、使用六页；顶部面板查看白名单文档和执行合同，Files定位原产物。这里描述已登记能力，本次没有启动应用。

例如审“下一批供料”的界面，依次查看当前批次运行、放入待料、下一拍满足条件后吸收三个状态；每个状态要标明是真实运行还是示意，并关联同一任务和版本。浏览器草稿意见导出回所属轮次后才成为长期记录。

`prepared`表示合同准备好，`active`表示会话打开，`closed`表示会话结束并释放所有权；卡片`done`也不等于验收通过。工作台没有自动组包、自动判定包失效、全自动阶段同步或专用对话审阅界面。你可以直接在对话中审同一份Markdown任务包，无须等待这些增强功能。依据：[展示规格](workbench-spec.md)。

## 怎样理解开发进度

把游戏看成由电脑主持的桌游：规则书说明怎样结算，规则执行保管真实局面，画面和声音表达结果，操作提交选择，存档负责延续。材料是否足够、谁受伤、何时胜败属于规则执行；换卡图或从3D转2D可能改变大量显示和输入，但不能让同一规则得出两个答案。

跟着一张卡看：设计确定开工、成本、D及失败；规则执行据真实状态开工、完工入手，再接受玩家上行，卡效处理结束后按权限回手或消耗；表现消费已发生事件；玩家通过真实对象操作；最后核对退出恢复和独立包。动画结束不能成为第二次扣费的入口，截图拍数也不能被写死为通用算法。一条链走通只证明限定范围可用。

| 阶段 | 用什么问题判断 | 应有的产物或证据 |
| --- | --- | --- |
| 设计准备 | 玩家为何选A而非B，代价清楚吗 | 可执行规则、真实内容、正反例与待验证假设 |
| P0 工程与交接 | 换干净目录还能打开同一版本吗 | 工程、固定依赖、独立包、恢复说明 |
| P1 规则可信 | 同一初态和操作能否得到符合规则的结果 | 真实状态、结算记录、规则检查、存档 |
| P2 能看懂并操作 | 知道发生什么、能做什么、操作后果吗 | 输入、布局、卡面、动画、音效、可达性 |
| P3 一场完整 | 能开始、打到胜败、恢复、重试和处理失败吗 | 完整单战及全链证据 |
| P4 一局完整 | 取得、构筑、携带与成长连起来了吗 | 路线、奖励、商店／休整、库存和节点恢复 |
| P5 可靠交付 | 值得反复玩，目标机器和存档可靠了吗 | 体验观察、内容包、性能、构建及资产来源检查 |

正式阶段条件沿[阶段计划](production-plan.md)。局部工作可以反复迭代，不用把阶段图理解成只能单向走一次。

| 看见的改动 | 它说明什么 | 仍要核对什么 |
| --- | --- | --- |
| 文字不拥挤、材质更合适 | P2可读性或视觉提高 | 条件可发现、信息公开、实际尺寸与真实状态 |
| 牌会翻转、移动、离场 | 有事件表现 | 真事件触发；暂停、单步、载入、失焦归位 |
| 换了一个模型 | 有表现资产 | 宿主尺寸、遮挡、命中、性能与来源条件 |
| 保存失败后不再错操作 | P1／P3流程改善 | 独立包、异常恢复及相关回归 |
| 完成一场胜败 | 有限定P3闭环 | P4取得构筑、P5反复游玩与可靠交付 |

看交付只需先抓三问：**玩家现在能做什么？这是候选、真实实现还是已检查结果？下一处缺口是什么？** 文件数、资产数、检查项数不能折算成整体完成率。技术通过、你接受画面、第一次玩的玩家能理解，以及长期有趣，是不同证据。

## 可复用提示词

以下都是模板，替换〈占位内容〉后使用；复制教学例子不代表本稿已启动这些任务。已有授权直接沿用，保留未知和未测，不另建重复报告。

### 1. 接手并解释当前项目

~~~text
请接手《言咒》，先按 E:/Project/game/yanzhou/AGENTS.md 和 development/README.md
读取当前5份启动文件，固定启动时设计提交；后续只按任务需要展开。
用通俗语言讲清：玩家做什么、当前设计范围、已有实现证据、主要缺口和下一步。
严格区分已采纳、已实现、已检查和待验证。
最后给我一个最适合继续的任务入口。本轮只读和讲解。
~~~

### 2. 探索一个新想法

~~~text
启动言咒探索：〈主题〉。我想解决的玩家问题是〈具体情景与不满意的结果〉。
先读 exploration/start.md 和 exploration/AGENTS.md；阅读模式CORE，
仅使用启动时已提交核心GDD，不读其他方向、历史或外部代码，不自动扩读。
先查探索入口的编号和标题，若已有本主题方向，定位后沿其登记范围续作；
主题不明确时先列候选名称，不读全部方向正文。确属新方向再分配未占用编号。
请用不同玩家选择、成本和失败后果比较少量方案，给推荐及未知，
需要我决定的内容按主题成组说明。摘要留所属README，暂不采纳、不实现、不测试。
~~~

已有方向直接把开头换为“继续DIR-〈编号〉，沿其登记版本和材料范围”；不要把CORE模板强加给既有方向。需要特定细则时明确加文件／章节，或授权在指定目录内按需展开。

### 3. 改一项现行设计

~~~text
我希望把〈现行行为〉改为〈目标行为〉，目的是〈玩家价值〉。
按当前开发启动入口及设计流程工作；允许读取与该行为直接相关的规则、
内容、案例、验收和正式来源，公共机制须追完整影响，不读其他探索或代码。
先查已有决定，用一个正常故事和会改变选择的反例解释改前／改后；
按必要流程补齐资格、提案／评估及Draft Change，形成可审的具体文本。
新的设计取舍集中交给我判断；已有明确采纳授权直接沿用。
确认采纳后同步权威设计、验收预期和受影响任务包，提交推送，仅记录决定摘要。
本轮不执行游戏实现或玩法测试。
~~~

收到具体方案后，可明确回复：“采纳本轮列出的〈方案／条款〉，范围为〈范围〉；其他未列出或仍待决项不包括。按该范围更新现行设计及派生输入。”

### 4. 实现一项已经定好的行为

~~~text
请在〈明确的实现仓库〉实现／核对〈一个可见行为〉。
先按言咒开发入口读5份启动文件，选〈现有任务包或行为〉，
按触发条件补读相关细则，固定设计提交、代码起点及内容／资产版本。
给出范围内外、正常／失败／恢复预期，在所属任务记录保存最小设计输入。
这次授权范围内的代码修改、必要自动检查、构建及本机运行核对；
不新增玩法、不运行额外玩家实验、不发布。
纯规则修复按预期→修复→受影响检查；新重点交互按现行四阶段规范制作。
遇到设计取舍按第8节暂停本批并交设计对接，规则唯一的工程偏差直接修复。
交付一个主入口、实际结果与证据、未测项、下一步及各仓库提交。
~~~

例如填“调整下一批待料，当前批次保持”，包选`future-purpose.md`。代码已存在时先核对差异，不重复造一套实现；CORE-068是否已接入以实际检查为准。

### 5. 通过对话审阅设计或交付

~~~text
带我审阅〈行为／变更／提交或运行包〉，按 development/design-review.md。
固定本次范围和版本，先讲旧行为与变化，再用正常故事、真正适用的失败反例、
一张关系／时序／状态图解释选择、成本、时机、胜负和信息公开。
审实现时展示预期→实际→固定证据，并标明真实运行、示意和未测。
把已有规则解释与需要我决定的新方案分开；不要将“理解了”当作新采纳。
每轮聚焦一个行为，可成组提出相关取舍；仅记录我的判断摘要与处理结果。
最后一行说明已覆盖、未覆盖和待决。本轮只审阅，不执行改规则或代码。
~~~

如果你已明确要求边审边改，把末句替换为具体授权范围；不要默认把一次意见扩成整套重做。

### 6. 查看进度或交接给下一位

~~~text
请根据〈所属任务记录〉和固定产物说明本轮状态：
玩家新增或修复了什么能力，处于哪个阶段，产物在哪，检查了什么，哪些还没测，
是设计待决、工程偏差、制作中还是范围外，下一步由谁处理。
核对任务包是否与权威设计同版本；代码、包和资产分别注明实际版本。
若使用工作台，展示同一来源和2—3个代表状态，意见回到所属轮次。
不要将会话closed、任务done或检查项数量当作验收完成。
交接只补变化与未决，不复制GDD、日志或另建进度数据库。
~~~

这些提示词围绕现行入口发出任务，执行者仍按适用规范处理版本、资格、Git和写入范围。人的精力留给有行为后果的选择；agent负责准确展开、实现、核对和回写。
