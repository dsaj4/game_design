# 看懂游戏开发的进度

2026-10-18 · game-002 · DevelopmentGuide。你不必先掌握引擎和编程，先看每次工作给玩家增加了什么能力，以及哪一段还没有连起来。当前事实与固定版本随[开发状态](README.md)更新，本页解释它们的含义。

## 先把游戏看成一场由电脑主持的桌游

规则书告诉主持人怎样结算；主持人保管真实局面；棋盘和卡片让玩家看见局面；玩家通过操作表达选择；存档让中断后能继续。电脑游戏还要把开始、结束、重试、成长和交付连接起来。这个类比只用于理解职责，不改变言咒的规则。

```text
设计规则与内容 → 规则执行 → 真实局面与事件 → 画面、声音和反馈
                    ↑                         ↓
                    └──── 玩家提交操作 ───────┘
                             ↓
                         保存与恢复
```

“内核”在这里指决定真实结果的规则执行：材料是否足够、何时完工、谁受到伤害、何时胜败。表现负责让你看见结果。换一张卡图或从3D转2D，可能重做许多显示和输入，却不应让同一规则结算出两个结果。

## 从想法到可交付游戏

```text
明确玩家选择
    → 一套可执行规则与真实内容
    → 能看懂并操作的一场战斗
    → 战前、战后与成长连成一局
    → 内容、体验、性能和交付逐项可靠
```

这不是只能走一次的流水线。你会在某个局部来回修改，但每次要知道自己补的是哪项能力。

| 阶段 | 你能用什么问题判断它 | 常见产物 | 当前言咒的含义 |
| --- | --- | --- | --- |
| 设计准备 | 玩家为什么要选A而不是B，代价能说清吗 | 规则、内容、正反例与待验证假设 | 主动调度与积累兑现仍要完善；画面不能替你作这个决定 |
| P0 工程可运行与交接 | 换个干净目录能打开同一版本吗 | 工程、固定依赖、独立程序包、恢复说明 | 既有Godot有包与复制检查；新方向还没有工程 |
| P1 规则可信 | 同样的局面和操作，结果是否稳定且符合规则 | 真实状态、结算记录、规则检查、存档 | EX案例已有底座，范围外规则和所有内容不自动完成 |
| P2 能看懂并操作 | 我知道现在发生了什么、能做什么、点完有什么后果吗 | 输入、布局、卡面、动画、音效、可达性 | 3D有运行预览，仍有视觉候选与理解待验证 |
| P3 一场完整 | 能开始、打到胜败、退出恢复、重试，并处理失败吗 | 完整单战包和整条流程证据 | 旧0.4有限定完整单战证据；新表现须重新对照全链 |
| P4 一局完整 | 战斗之外的取得、构筑、携带和成长能连起来吗 | 路线、奖励、商店／休整、局内库存与节点恢复 | 尚未启动；不是再补几张图就完成 |
| P5 可以可靠交付 | 内容值得反复玩，目标机器稳定，存档和资源来源可靠了吗 | 体验观察、内容包、性能和构建／来源检查 | 仍有较多未完成项；没有可信的整体完成百分比 |

阶段的正式退出条件见[阶段计划](production-plan.md)。现在选择先完善首场核心玩法，是缩小下一次实现的输入范围，不是宣称路线和成长不重要。

## 跟着一张行动卡走一遍

以“法器完成加工，行动卡随后生效”为例：

1. **设计**说明何时开工、怎样承诺材料、D是多少、什么情况下失败。依据在[法器规则](../design/systems/artifact-system/rules.md)和具体案例。
2. **规则执行**据真实状态决定是否开工，记录加工，满足条件时完成并入队。不是按某张截图的拍数写死结果。
3. **表现**读取已发生的事件，让法器亮起、卡片出现，展示正确名称和公开信息。动画迟一点结束不应多扣一次材料。
4. **玩家操作**需要对应真实对象：点到的是哪张牌、能查什么、暂停后是否静态、关闭后是否仍停。图像看上去正确还不够。
5. **保存与检查**确认中途退出后不会重复发牌、重复支付或重播已提交动作；再在独立包里核对这条链。

```text
文字说清规则 → 示例给出预期 → 实现得到真实结果
                                  ↓
                         画面与操作表达这个结果
                                  ↓
                         检查／审阅／失败记录
```

一条链走通证明这条链在该范围可用。更多卡种、复杂标记、多牌批次和整局路线仍有自己的规则、内容和失败情境。

## 画面修好了，在开发中占什么位置

| 本轮工作 | 实际贡献 | 仍需连接的能力 |
| --- | --- | --- |
| 卡片文字不再拥挤 | P2的信息可读性提高 | 条件是否易发现、暗牌是否安全、点击与真实状态是否一致 |
| 桌面材质不再像塑料 | P2的视觉目标更接近 | 规则、可操作性、完整战斗和性能并未因此自动改善 |
| 牌会翻转、移动和离场 | P2把事件表达出来 | 是否由真实事件触发；暂停／单步／载入／失焦时能否正确归位 |
| 替换了一个模型 | 获得可用的表现资产 | 放到实际宿主后的尺寸、遮挡、命中、运行成本和来源条件 |
| 修好了保存失败后的操作 | P1／P3保护局面与完整流程 | 独立包恢复、异常路径和其余功能回归 |
| 完成一场胜败 | P3闭环有了 | P4取得和构筑循环、P5反复游玩与可靠交付 |

一次视觉修复可以很有价值，但它通常只改变其中一行。报告应说明修复的场景与剩余能力，而不是把它换算成“游戏又完成了10%”。

## 我该怎样看一份交付

先看主入口和关键前后对照，再看三句话：

1. 现在玩家能够做什么，是新增能力还是已有能力的修复？
2. 这是候选图、真实实现，还是已经在固定包中检查过的结果？
3. 还差哪个环节，下一轮要补什么才能继续？

“19件资产完成”“80项通过”分别说明一个产物范围或检查集合，不能单独说明整场游戏已完成。用户视觉接受、技术检查和真人体验也不同：你喜欢这个画面，不等于第一次玩的人能理解；程序没报错，也不等于玩家愿意继续玩。

## 你想改什么，就从哪里开始

| 想改变的东西 | 先看哪里 |
| --- | --- |
| 玩家能做什么、有什么代价 | [当前设计问题](../governance/questions.md)与对应rules；需要变更走正式来源链 |
| 卡面、布局、图形和说明方式 | 对应visual设计记录与[制作小循环](iteration-spec.md) |
| 点击不对、结果不对、保存或包有问题 | [实现仓库](E:/Project/yanzhou-godot/README.md)的当前范围和报告 |
| 不知道现在该看哪份文件 | [开发状态](README.md)和工作台当前入口 |

目前可以先忽略类名、渲染管线、文件格式和构建命令。只有它们影响你的设计选择、表现代价或交付范围时，执行者才需要解释。

你可以这样给下一轮指令：“先说清这项修改给玩家增加了什么能力、位于哪个阶段；给一个能审阅的代表情境，沿现有规则完成最小循环，最后告诉我还缺哪几步。”
