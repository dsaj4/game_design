## 开工只走这一条路

1. 读完[核心正文](../design/GDD.md)和本页；用[开发入口](README.md)确认当前能力与制作范围。已注入的AGENTS不重复加载。
2. 用一句话确定玩家行为，再按[行为索引](../governance/rule-index.md#按行为选细则)选择现有包或组合相关条款。只读涉及的章节，不递归跟随全文链接。
3. 在所属任务记录**一次固定整个设计仓库的完整提交号**；包、核心、引用细则均从该提交读取。示例明确冻结的上游输入另列例外，不能换成最新。尚未创建执行任务的包不伪造执行版本。
4. 核对包中的行为、引用与该版本一致。读包即可得到明确答案的内容不重读全系统；涉及公式、调度算法、未覆盖对象或改动来源本身时，按包列出的条件展开细则。
5. 用包里的正常、失败及恢复情境核对可实现性。缺少会改变结果的设计就列出缺口，按已有裁决流程处理；已授权且规则明确的工作直接继续。

一般任务不加载完整GDD包、来源沿革、全部问题清单或全套验收。改变公共总序、对象生命周期或通用支付时需要读取所有受影响接口，不能用窄包隐去依赖。用户明确材料白名单优先。

## 新包的最小内容

以下写在现有设计／开发轮次里即可；只有可复用且跨文件的行为才独立放到task-packs，不为每个小修新建文件。

| 内容 | 写到什么程度 |
| --- | --- |
| 目标与范围 | 玩家做什么；当前制作范围；本包不处理的相邻行为 |
| 版本与来源 | 共同提交由任务登记一次；必要条款、内容／案例定位；继承的固定输入例外 |
| 最小行为 | 前提、操作受理、状态变化、费用、失败、终局及恢复；无关字段省略 |
| 条件展开 | 哪种改动触发哪组细则；缺失的内容保持Unknown |
| 可核对情境 | 正常故事、会改变选择的反例和必要恢复；引用已有案例，不复制完整逐拍表 |
| 交接结果 | 设计已明确／待决；实现与检查的状态和固定证据入口，仅在任务实际执行后填写 |

每段派生内容邻接来源定位；引用若只给系统目录还不足以开工。参数在权威内容页维护，包中用于讲解的数值必须指明案例。开发agent可更新任务范围、问题与执行证据，改变设计先回对应权威页，不直接把包改成新规则。

## 变更后怎样同步

改源条款时搜索活动包中的文件路径／规则ID，复核必要输入、情境和条件展开；只改措辞则核对等义，改变行为则更新采纳依据与受影响包。未完成复核的包标“待同步”，停止把它用于新实现。包与权威来源有冲突时按来源纠正并保留实际偏差，不择一猜定。

正文短不是完成标准。执行者应能回答“现在能做什么、什么时候生效、失败损失什么、恢复会不会重复”，审阅者应能判断其中的行为取舍。实现检验沿[小循环](../standards/iteration-spec.md)，人工讲解沿[场景审阅](../standards/design-review.md)。
