# 设计与开发小循环规格

2026-10-23 · game-002 · DevelopmentPolicy / G002-DOC-026／028。依据[Q3答复](../sources/inbox/2026-10-18-development-system-review.md#本轮批量澄清)及本轮任务包与审阅规范，按变化裁剪、保留必要证据。规则资格、设计裁决和实验授权仍沿原规范。

## 一个循环解决一件可见的事

一轮应能用一句话描述结果，例如“在主桌尺寸下识别条件牌，并能到近观查完整分支”，而不是“完成全部UI”。同一轮保留同一对象、状态、输入版本和审阅记录；换执行者不等于重开任务。

```text
定义本轮变化 → 做最小可审产物 → 在目标情境核对 → 记录结果与下一步
                                  ↓ 不满足
                            定位差异后返回本轮
```

四步是工作循环；文字、HTML、效果图、实现是可能需要的产物。新重点交互仍按这四类产物的依赖顺序推进。先让一个代表状态走通完整链，再扩展变体和数量；不先量产一组孤立效果板再发现主桌放不下。

## 四步各交什么

| 步骤 | 最小记录或产物 | 进入下一步的条件 |
| --- | --- | --- |
| 定义 | 玩家或审阅者要看见的变化、规则／问题ID、当前问题截图或例子、范围与验收场景 | 输入可定位，预期唯一；真正设计取舍进入DOC-024，不由实现者补默认规则 |
| 小样 | 本轮需要的新文字、交互示意、效果或样件；复用的旧稿列固定版本 | 一项主要问题有可查看答案；不是只有制作说明或“已生成” |
| 情境核对 | 对照真实目标尺寸、宿主、邻接对象、输入路径和必要异常状态；运行变化检查真实结果 | 说明哪个范围通过、失败或NotRun；不能以可解析／可打开代替正确表现 |
| 收口 | 差异结论、证据、固定提交、原件／派生关系、未决与下一轮动作 | 下一位执行者能找到输入和产物，知道哪些决定沿用、哪些未完成 |

用户已经授权的可逆工作可以继续，不把每一步都变成审批。只有需要用户作设计取舍、明确接受某个候选或额外执行授权时才集中提问。未答部分保持未知；不能把沉默写成接受。

## 按任务选产物

| 任务类型 | 本轮必要路径 | 可以复用或不适用的内容 |
| --- | --- | --- |
| 新重点交互或实质信息结构变化 | 文字／状态 → 可操作HTML → 代表状态效果 → 真实接入与对照 | 复用已有字体、模型、图标与规则；各阶段仍需对应产物和复核 |
| 已确认交互的小视觉修改 | 标出本次差异 → 原尺寸前后对照 → 真实宿主核对 | 引用原文字、HTML和已确认效果，不为同一目标重生整套稿；出现信息／交互变化时转上一行 |
| 纯规则实现或技术偏差修复 | 明确预期／复现 → 最小修复 → 受影响检查 | 无视觉变化时，HTML／效果图可记NotApplicable并给理由；不跳过回归或失败路径 |
| 资产制作或替换 | 使用情境、尺寸与来源 → 一个样件 → 在真实宿主核对 → 扩量 | 现成资产优先；工具调研仅在存在具体缺口时触发，不设固定“调研阶段” |
| 主系统设计 | 意图与对象 → 候选／取舍 → 资格与必要变更 → 可实现输入 | 按原设计流程决定是否需要M／P／E／D，不用小循环绕过采纳 |
| 文档治理 | 读写范围 → 职责／迁移 → 链接与一致性核对 → 固定取证 | 不要求游戏HTML、效果图或引擎运行 |

复用不是省略：写明“沿用哪一版、为何仍适用、本轮检查了哪个差异”。NotApplicable必须基于任务性质；缺少时间、工具失败或尚未打开只算NotRun。阶段检查失败时保留失败记录；若缺口不影响限定后续工作，列明限制、受影响验收和继续依据，最终不能把该阶段补记为已通过。涉及规则取舍仍执行整批暂停。

## 一轮记录放在哪里

设计制作放所属visual或方向README；实现放代码仓库现有协调／交付记录；治理结论放所属规范或决定，不要求另建报告。跨系统的最小设计输入可复用[任务包](task-pack.md)，人工讲解按[场景审阅](design-review.md)。已有DQ、CARD-01等对象ID继续引用，不再建立全局任务库。循环身份用“所属记录路径＋R01/R02”，同一目标修订沿用，固定旧版本保留。

每轮只要求以下信息；技术细节和大清单链接到原记录，不抄进工作台：

| 信息 | 要回答的问题 |
| --- | --- |
| 目标与阶段 | 这次改变什么，位于P0—P5哪一阶段，属于哪个已有任务／问题 |
| 输入与授权 | 哪版设计、代码和资产；允许哪些材料和动作；哪些不在本轮 |
| 责任与依赖 | 谁维护哪份文件，依赖谁的结果；小任务可一人完成 |
| 产物 | 文字、示意、效果、源件、运行、证据分别在哪里；哪些为复用 |
| 进度 | 当前处于定义／小样／核对／收口哪一步；为什么阻塞、下一动作是什么 |
| 审阅 | 对哪个固定产物、哪个场景提出什么问题；处理依据和复核结果 |
| 完成证据 | 预期与实际、检查方式、代码／包／资产版本、通过／失败／NotRun |
| 交接 | 剩余项归哪里、下一轮输入与完成条件；用户决定摘要及范围，按[轻量记录](../../docs/design-workflow.md#言咒轻量记录)共用版本与证据引用 |

工作台只展示这些记录的摘要与入口。设计输入在任务共同提交记录一次，包与细则继承；本机执行合同按工具需要保存材料校验、文件所有权和会话状态，文档不重复抄录。长期结论不能只留在本机合同、聊天或浏览器缓存。

## 中间产物怎样登记

每个产物至少关联“本轮 → 对象／状态 → 载体与用途 → 版本 → 查看入口 → 来源／派生 → 复核结论”。一个包可以有多张截图，不为每张过程截图建立新AS；具有独立复用价值或许可差异时按DA-1分配身份。

| 载体 | 它能帮助审阅什么 | 不能冒充什么 |
| --- | --- | --- |
| 文字／状态表 | 玩家行为、字段、条件、异常和范围 | 已实现或玩家一定理解 |
| HTML | 布局、路径、状态切换与阅读密度 | 引擎逻辑／真实输入通过 |
| 效果图／关键帧 | 风格、层级、镜头、材质和意图 | 全状态覆盖或可运行功能 |
| 源资产／派生资产 | 可编辑性、格式、来源与适配 | 在游戏中已使用或许可可分发 |
| 真实运行截图／录屏／包 | 指定版本的真实表现与操作结果 | 自动证明全部规则、性能和体验 |
| 检查报告 | 指定输入下的结果与失败 | 用户接受、玩法好玩或范围外通过 |

意见先关联固定产物，再关联对象与状态。修改后原意见标为已处理／暂缓／不采用并说明依据，不覆盖原对照图，也不删除不采用的独有失败路径。UI-REVIEW的浏览器草稿要导出并回填所属轮次，才算长期登记。

## 怎样算完成

任务收口要求：范围内产物可访问；需要的检查有结果；已知阻断缺陷已解决或由用户明确排除；未验与延期有去向；固定版本和下一步已记录。设计资格、实现状态、技术检查、用户视觉接受和真人体验分别报告。

交付时用一段人话回答：**“这轮让玩家能够……，属于P…；实际检查了……；还没有完成……；下一轮要解决……。”** 不只报文件数、组件数或检查项数。

实际治理轮示例见[本轮记录](../governance/development-review-2026-10-18.md#本轮制作循环)。新重点交互的四阶段要求继续见[开发规范第9节](development-standard.md#9-每项重点交互的四阶段制作)。
