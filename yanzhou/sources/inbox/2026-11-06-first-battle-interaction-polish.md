## 当前玩家动线与优化原则

新战／继续 → 战前查看与配置 → 选择材料、投料及排期 → 推进本轮5拍 → 收货与最终布置 → 确认整轮、锁行交锋 → 未终局进入下一轮；胜利进入选留，失败进入回看与重试。

生产期间也可以调整战斗行；五拍结束后不限时最终布置。查看、暂停、取消和保存恢复贯穿全程，不解除已冻结工序或战斗锁行。当前选留后没有下一场。

1. 主桌仅保留人工设计选定的必要状态、对象和当前操作。设置统一进入其他页面；完整说明进入对应对象详情页。
2. 选中、拖动或发生异常时提供短暂、贴近对象的必要反馈；不要借这些状态重新铺满长期说明。
3. 悬停和拿起是预览，投料形成可改草稿，开工才冻结；对象位置、动画和声音对应实际承诺。
4. 动画只表现已提交且允许公开的事实；减动效、静音和加速仍保留状态与顺序信息。
5. 先完成被否定区域的人工设计，再制作代表性样件；避免在旧法器布局或旧详情结构上直接堆美术与动效。
6. 先确定整桌共同约束，再逐组件完成设计、美术、开发和整桌复核；每个组件独立可审阅，也必须在实际动线中成立。

## 真实组件的拆分与整体开发安排

用户希望从桌面、筹码、卡牌等对象出发逐个设计。建议将“真实组件”定义为：有清楚职责、尺寸与锚点、可见状态、输入行为、动作和组合关系，能独立展示并在正式场景中复用的单元。具体边界是本轮流程建议，尚非已定技术架构；组件化本身不要求3D、物理碰撞或真实动力学，呈现技术由实现仓库按效果需求与成本决定。

当前主场景由[界面脚本](E:/Project/yanzhou-2d/scripts/battle_ui.gd)集中生成，大部分区域仍不具备独立制作与复核的宿主；已有[卡牌动作层](E:/Project/yanzhou-2d/scripts/battle_card_motion.gd)可以作为局部拆分起点。开发侧需安排表现拆分和渐进接入，保留既有规则、身份与保存边界。此处只记录范围和交接要求，具体场景、接口和代码组织留实现仓库。

### 按四个层次划分职责

| 层次 | 建议组件 | 可逐个设计的内容 | 需要整合决定的关系 |
| --- | --- | --- | --- |
| 单个对象 | 玩家卡牌、敌牌、单枚筹码、法器、炉心 | 形态、尺寸、材质、可见状态、拿放与运行等局部动作 | 对象在不同区域中的身份连续性、尺寸变化和信息权限 |
| 对象容器与桌面环境 | 手牌区、战斗行及列位、筹码堆、法器区、配置网格、桌面 | 排列、容量表现、落点、局部遮挡、接触关系；桌面负责基础环境和光影 | 对象移入移出、区域间空间、飞行动作路径和整桌视觉重点 |
| 页面 | 对象详情页、设置页、菜单、战果及选留页 | 信息结构、进入／退出、焦点和必要操作 | 只读或可编辑时机、与桌面对象的关联、暂停及返回状态 |
| 跨组件协调 | 拖动与焦点、阶段切换、事件表现、声音、布局与可达性约束 | 全局规则先统一，局部对象依此制作 | 同时只能有一个明确操作对象；多对象动作顺序、取消和终局截断一致 |

单卡与手牌区分别设计：单卡负责自身形态和状态，手牌区负责排列、分页与选取关系。单枚筹码与筹码堆分别设计：单枚负责外观，筹码堆负责数量表达、排列和增减。法器本体与法器区分别设计：本体负责器形及运行，区域负责投料、工序、出料和相邻对象关系。桌面是环境组件，不把全部交互重新集中进“桌面组件”。

图像图层、设计组件和开发单元无需机械一一对应。纸纹和阴影通常属于组件内部图层；只有存在独立状态、操作或复用需求时才继续拆分。共享卡牌基础表现可以承接玩家卡和敌牌，但敌牌的信息公开和行动状态必须独立定义。

### 每个组件的最小交接内容

以下内容合并在所属任务中，不另建一套组件台账；实际进入制作时才建立对应产物。

| 交接内容 | 设计负责人先给出 | 美术与开发共同核对 |
| --- | --- | --- |
| 职责与归属 | 对象是什么、由谁操作、出现在哪些区域，哪些是实物／库存、哪些是记录 | 换区域或表现不复制对象，不由动画新增资源 |
| 空间 | 基准尺寸、可缩放范围、锚点、净空、遮挡与触区 | 原件边缘、实际轮廓、碰撞／点击边界及文字可读性分别核对 |
| 状态与信息 | 默认、悬停、选中、拖动、不可用、运行、结果等实际需要的状态；各状态允许看到什么 | 静止画面可辨，动态过渡不泄露暗牌或形成假库存 |
| 操作与事件 | 可做动作、前置条件、取消、失败和返回；变化由什么事实触发 | 点击／键盘等价；规则确认与动作播放分工明确 |
| 动作交接 | 来源与目的锚点、动作起止、跨区过渡、声音、暂停和减动效 | 跨组件动作有统一编排责任，不由两端各播一份或各提交一次 |
| 复用与验收 | 共同部分、内容差异、真实尺寸及代表场景 | 静态、动态、整桌合成、运行行为分别通过；固定输入版本及已知限制 |

### 用小循环代替全部设计完再集中开发

1. **先建立整桌草模。** 18确定页面与区域关系、尺寸、光向、层级、输入及动作交接约束。使用简单占位即可，保留已过关桌面基础形态；不等待全部美术定稿。
2. **先打通一张卡。** 02完成单卡及其状态，连同手牌容器、一个合法列位和详情入口完成代表路径；走文字→HTML→美术效果→实际接入。这样能尽早发现尺寸、质感、焦点和动作之间的矛盾。
3. **再做一套筹码、一台法器。** 筹码外观样件可先行；生产、入列等行为须等16明确逐类语义。法器先完成14的区域组织，再连03、05和13跑通投料、加工、到货、详情与返回。
4. **每件完成即放回整桌。** 用19的组件预览及20的整桌集成同时复核，检查多对象遮挡、视觉密度、输入竞争、动作去向与低分辨率表现；问题在本组件闭环中修正。
5. **代表链通过后扩量。** 扩为完整手牌、敌牌、四器和筹码状态，再补配置及战果；实际效果回到12人工复核。桌面最终光影在真实对象摆齐后收口。

设计、美术和开发可以沿已明确的组件滚动推进：一个组件进入美术时，另一个可以继续设计；开发及早提供可行性和接入反馈。对应重点交互的前三阶段仍须完成后才进入正式重写，不以样件替代设计取舍，也不要求整个游戏全部设计完才开始接入。

### 整体开发需要额外控制的成本

- **共享标准先收口。** 卡牌、筹码和器具分别精修前先对齐比例、光向、描边、阴影、文字和状态语言，减少最后拼合时大面积返工。
- **性能与材质效果一起衡量。** 在预计同时出现的对象规模下检查堆叠、透明层、阴影和飞行动画；预算由开发核实。物件有实体感不等于每枚都必须作物理模拟。
- **复用正式组件。** 组件预览与游戏使用同一套实际对象和资产；预览中的展示状态明确标识，不建立第二套玩法或另一份正式实现。
- **逐区域替换。** 以当前可运行首战为基线，每接入一件检查相关规则、操作和恢复，再替换下一件；不同时推翻规则模型、保存和全部界面。
- **明确完成条件。** 单件效果认可、动线可操作、整桌合成成立和工程检查通过是不同结果；只完成独立美图不能把该组件标为完成。

每项任务统一按**设计任务 → 美术任务 → 开发任务 → 单件与整桌复核**交接。设计产物给出信息结构、操作、状态和可操作示意；美术产物给出同结构效果及可接入资产；开发以明确版本接入并回到设计复核。没有美术新增的任务也要核对复用资产与显示状态，不能直接跳过效果一致性。

## 任务清单

### 20 分组件渐进集成与整桌回归

- [ ] **设计任务：** 定义每次替换的代表动线、相邻组件关系及完成条件；跨区动作有唯一编排责任，逐项核对与用户人工反馈的对应。
- [ ] **美术任务：** 每接入一件即提供真实整桌合成与连续动作对照，修正相对尺寸、光影、密度和动作路径；全量对象接入后完成桌面光影收口。
- [ ] **开发任务：** 保留当前首战规则与保存基础，按组件逐步替换表现；在相关操作、事件顺序、取消、暂停、恢复及低分辨率场景中验证，清理被替换的重复表现路径。
- **交付与验收：** 每批有可运行首战、固定组件及资产版本、实际检查和未决项；独立组件与整桌使用相同产物，跨组件不重复提交、不串输入、不形成第二份库存。
- **依赖：** 18、19及当前批次组件；与12配合，工程验证、人工视觉接受和玩家实验分别记证。
