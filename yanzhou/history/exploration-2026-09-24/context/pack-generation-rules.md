# game-002 Context Pack 生成规则

规则版本：v2。状态：`Ready / Core Design Only`。日期：2026-09-09。

本规则和[来源配置](generation-profile.json)规定如何生成背景包，不是已生成的背景，也不是可执行生成器。当前按用户确认只提取核心设计，不增加实现、实验和研究计划约束。

## 1. 输入与使用方

- 唯一来源项目：`game-002`，来源根 `workspaces/game-002/`。
- 唯一使用项目：`game-002-optimization`，输出根为本 context 目录。
- 配置中的 `sources[].path` 均相对来源根，是明确文件清单，不是通配符或递归发现指令。
- 每次生成明确选择一个已存在的完整 Git commit，记录为 `source_commit`。可以将启动时的 HEAD 解析一次后锁定；后续步骤不能重新读取浮动 HEAD 或混用工作树文件。
- 来源工作区有未提交变更时，报告“包不包含这些变更”，继续使用已固定提交或明确先保存新版本。不得把旧 commit 标签贴在未提交内容上。

当前 v2 列出 6 个必需来源：词汇、正式核心与决策、合格素材索引、首轮全局基线和基础数值框架。基础来源的注册不包含全部 40 份素材正文、任何 inbox 正文、原型观察、当前问题、开发索引或外部实现。

## 2. 生成步骤

1. 核对目标 Project ID 与项目注册表；new-roguelike 不能作为输出目标。
2. 读取并解析来源配置，固定 profile 版本、profile 文件摘要、profile 所在提交及 source commit。两者可以不同，但必须分别记录。
3. 从 source commit 逐项读取普通文件的原始 Git blob 字节，检查路径、文件类型与必需项；不使用工作树的 mtime 推断版本，不跟随符号链接。
4. 在输出根下选择唯一 `baseline-YYYY-MM-DD-NNN` 目录名。已有目录即拒绝覆盖，序号递增；路径必须解析后仍位于目标 context 根内。
5. 保存原始字节到 `sources/<来源根内相对路径>`，逐文件记录 SHA-256、字节数、角色和源状态。不得通过 PowerShell 文本管道改变换行或编码后再声称字节一致。
6. 从这些来源撰写 `context-pack.md`，按下述章节生成背景摘要；每条设计陈述关联来源文件和章节，区分历史、候选与当前范围。生成的 Markdown/JSON 使用 UTF-8 无 BOM、LF 换行，写入最终字节后再计算摘要。
7. 生成 `source-manifest.json`，将 profile、source commit、包含/排除清单和摘要产物全部固定下来。
8. 完成完整性、来源及状态审查，写 `validation.md`。缺失和矛盾不能填猜测；检查未通过的目录保持 Draft，不激活。
9. 检查通过后封存包，更新 context/README、项目注册表和来源注册表，指向同一个活动 pack ID。提交推送时仅包含该生成任务的文件。

输出结构约定如下，当前尚不存在任何实例：

```text
baseline-YYYY-MM-DD-NNN/
  context-pack.md
  source-manifest.json
  validation.md
  sources/
    README.md
    CONTEXT.md
    game-design-workflow/...
    research/...
    docs/...
```

原始快照内的链接保留原样，可能指向未打包内容；它们是出处，不是离线包内容或追加读取授权。摘要中的本地链接必须指向本包实际文件；核心设计之外的依赖不加载，也不作为生成失败条件。

本目录 `.gitattributes` 对生成的 Markdown/JSON 固定 LF，对 `baseline-*/sources/**` 禁用 Git 文本转换，保持源 blob 原字节。不能对 sources 另作格式化；提交及检出后的来源摘要仍须一致。

## 3. 摘要章节

| 章节 | 必须说明 |
| --- | --- |
| 包身份与范围 | 使用项目、source commit、profile 版本、来源数、明确排除项 |
| 当前设计状态 | 正式核心是否采纳；管理 Accepted 与玩法 Accepted 分开 |
| 项目背景与词汇 | 目标情境和关键概念，保留新旧定义的适用范围 |
| 已确认工作基线 | 只从已打包合格素材提取；保留 Qualified/Hypothesis，不升格为体验验证 |
| 主要系统与关系 | 只写已加载内容；索引引用的正文未装入时注明尚未加载 |
| 数值与实验边界 | 已确认试算锚点、实验性词义/数值、范围与未测内容分开 |
| 设计边界 | 本轮可使用的核心设计前提、未采纳内容与明确 Unknown |
| 历史与冲突 | 来源相互不一致或已失效旧口径；实现与实验细节不进入本包 |

README、CONTEXT、current-questions 和素材索引都可能混有历史输入，不能把整份文件标成“全部已确认”。基础来源允许保存这些文件的原始快照，摘要中只提取有明确来源状态的部分，未确认表达仍为未确认。

## 4. 来源判断优先级

- `core-concept.md` 与 `decision-log.md` 决定正式采纳状态。空白核心不能用 README 或代码结果填满。
- 合格素材决定其明确范围内的规则选择，Hypothesis、后置范围及修订说明必须一起保留。新时间戳或新文件名本身不能证明覆盖旧规则。
- 已有材料的明确覆盖说明用于解释新旧关系；仍冲突时逐项列出，不由 agent 静默选一版。
- 项目开发索引仅对实现登记负责，不决定玩法采纳。历史 README“无代码”的说法与较新索引相冲突时，注明时间与范围，不能借此否定已有外部样片。
- 原型/模拟观察只对注明的实验条件有效；索引中的报告链接不能当作已经加载报告正文。

生成前已知需要关注的两类设计边界：核心仍为 Unknown 而材料已有工作基线；旧固定词类与后续灵活句式的适用范围。数值试算、原型观察和开发登记不在本包内判断。

## 5. Manifest 最低字段

采用 JSON 对象，UTF-8。下表是 v1 的字段契约，尚无可执行 JSON Schema。

| 字段 | 约束 |
| --- | --- |
| schema_version | 固定 `context-pack-manifest/v1` |
| pack_id | 与唯一输出目录名一致 |
| source_project_id / destination_project_id | 固定 game-002 / game-002-optimization |
| source_root / source_commit | 仓库相对根、完整已解析提交；所有源文件必须来自同一提交 |
| profile_id / profile_version / profile_commit / profile_sha256 | 固定生成规则配置身份及其 Git blob 字节摘要 |
| generated_at | 含时区的 ISO 8601 时间，不伪造 mtime 为发布日期 |
| sources[] | 每项有源相对路径、包内相对路径、Git blob ID、SHA-256、bytes、role、原状态及包含理由 |
| excluded[] | 未加载目录/文件/链接与排除理由；默认范围无需展开被禁止目录 |
| claims[] | 每条摘要陈述的 ID、来源路径、章节/行号和证据状态；无出处不得写成事实 |
| conflicts[] / unknowns[] | 冲突内容与来源、需补材料、不可得出的结论；无冲突可为空数组 |
| artifacts[] | context-pack.md 和 validation.md 的相对路径、SHA-256 与字节数；不包含 manifest 自身摘要以免循环 |
| validation_status | `Passed` 或 `Failed`；通过只表示包完整且来源审查通过，不表示游戏设计过关 |

## 6. 激活条件

- 6 个必需文件均存在于指定 source commit，均为普通文件；文件清单去重，路径不含父目录跳转、绝对路径或禁止目录段。
- source、profile 和全部输出摘要匹配保存字节；摘要里的引用指向真实来源，未加载内容不写成已知。
- 验证 context-pack 没有把管理决定、Qualified 材料、Hypothesis、模型观察或代码 Verified 混成玩法 Accepted。
- 技术完整性与陈述来源都通过检查，所有未决冲突已显式记录；阻碍本次优化的未知项必须在入口标明。
- 活动包指针在项目注册表、context 入口和来源注册表一致。包没有被登记激活前，不作为当前优化基线。

激活仅是背景使用决定；授权范围内 agent 可完成核验和登记，无须对同一来源清单反复要求用户确认。涉及新设计采纳、扩大跨项目读取或无法自行消解的实质冲突时，再提具体问题。

## 7. 刷新与失败

| 情况 | 处理 |
| --- | --- |
| 必需文件缺失或类型不符 | 生成失败，不补写内容、不激活不完整包 |
| 摘要没有明确来源 | 删除该摘要陈述或改为 Unknown，再审查 |
| 需要未包含的合格素材正文/实验报告 | 在 questions 写明原因，生成显式新增文件清单与新 profile 版本；先审查其角色和范围 |
| 指向 inbox、旧项目、另一探索项目或外部代码 | 不沿链接读取；独立任务授权与资格确认，不能借 profile 扩展绕过隔离 |
| 来源发生新提交 | 旧包仍能复现；记录更新需求，生成新包，不原地刷新历史来源 |
| 同名目录已存在 | 不覆盖，另选序号；失败目录不冒充正式包 |
| 构建中断 | 保存 Draft/失败说明，验证前禁止活动指针指向该目录 |

来源配置变更必须在同一任务说明新增/删除项和原因；只在允许的 game-002 来源根内补选已资格确认材料，不重复询问已授权的背景用途。引用未资格确认的原始想法仍不能把它写成工作基线。
