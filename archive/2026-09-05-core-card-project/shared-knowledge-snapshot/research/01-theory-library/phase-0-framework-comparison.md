# Phase 0 外部框架对照：游戏设计、迭代与发布

Page ID：`SRC-COMP-2026-09-04`

状态：`Reviewed / Proposed baseline`

版本：`0.1.0`

更新时间：`2026-09-04`

用途：为本仓库的 S0-S7 游戏开发阶段提供可审查的外部参照。本文不是“行业唯一流程”，也不把任何外部来源直接变成本项目已采纳的设计决策。

## 1. 对照范围

本轮选择三类互补来源：

| 来源 ID | 来源 | 能回答什么 | 不能回答什么 |
| --- | --- | --- | --- |
| `EXT-MDA-2004` | Hunicke、LeBlanc、Zubek，*MDA: A Formal Approach to Game Design and Game Research* | 机制如何引发动态，动态如何形成玩家体验；如何从体验反推规则 | 项目排期、团队分工、发布门槛 |
| `EXT-AGILE-PRINCIPLES` | Agile Manifesto Principles | 如何用短反馈周期、可工作的增量和持续反思管理不确定性 | 游戏体验质量的具体阈值、平台合规 |
| `EXT-STEAM-RELEASING` | Steamworks，Releasing on Steam | 发布候选、商店页面、构建和上线准备需要分别核对哪些平台事项 | 其他平台的要求、玩法是否有趣、市场成功概率 |

访问日期：`2026-09-04`。来源链接：

- [MDA 原文 PDF](https://users.cs.northwestern.edu/~hunicke/MDA.pdf)
- [Agile Manifesto Principles](https://agilemanifesto.org/principles.html)
- [Steamworks Releasing](https://partner.steamgames.com/doc/store/releasing)

## 2. 共同点

三类来源虽然对象不同，但共同支持以下工作方向：

1. 先定义希望观察到的结果，再选择机制、流程或发布动作；不能只堆活动清单。
2. 通过可观察证据缩短反馈周期。游戏设计中的玩家行为、迭代中的可工作增量、发布中的构建/页面检查，都比“感觉已经完成”更可靠。
3. 允许改变方案，但每次改变要能说明影响范围和下一次检查方式。
4. 需要区分不同层次的问题：机制与体验、工作节奏、平台交付条件不能用同一个“完成”状态表示。

## 3. 差异与边界

| 维度 | MDA | Agile | Steamworks | 本仓库处理方式 |
| --- | --- | --- | --- | --- |
| 关注对象 | 玩家体验的生成链 | 团队如何在不确定性中交付 | 一个具体平台的发布流程 | 用 MDA 写设计推理，用迭代原则组织阶段内工作，用平台清单核对 S6/S7 |
| 主要证据 | 机制、行为、体验之间的可解释关系 | 可工作的增量、反馈、回顾 | 页面/构建/配置/审查状态 | 统一记录来源、版本、观察和阶段门证据 |
| 时间结构 | 没有规定项目阶段 | 鼓励短周期，但不规定游戏项目的固定阶段名 | 按平台发布条件组织步骤 | 采用 S0-S7 作为职责基线；阶段内部节奏可迭代 |
| “完成”含义 | 体验推理能够自洽 | 当前增量可工作且可检查 | 平台要求满足并可上线 | 每个阶段分别写 Go/Iterate/Park/Stop，不互相替代 |
| 适用风险 | 机制和体验错配 | 需求变化、反馈延迟、沉没成本 | 发布阻断、页面/构建不一致 | 将玩法、生产和发布风险分开，并保留回退方案 |

## 4. S0-S7 采用理由

本仓库采用以下“共同骨架”，而不是照搬任何来源的目录：

| 阶段 | 采用的外部支撑 | 本仓库的解释 |
| --- | --- | --- |
| `S0 研究与问题定义` | MDA 的体验目标思路；Agile 的价值/反馈导向 | 先说明要解决的玩家或制作问题，以及当前未知 |
| `S1 概念与预制作` | MDA 的机制—动态—体验推理；课程 `E-SJ002-P004-001`、`E-SJ002-P009-001` | 把概念、支柱、核心循环和原型问题写到可复述 |
| `S2 原型与趣味验证` | MDA 的运行结果观察；课程 `E-SJ003-P001-001`、`E-SJ003-P024-001` | 用低成本可玩版本验证主要未知，不以美术完成度替代体验证据 |
| `S3 垂直切片` | Agile 的可工作增量；课程 `E-SJ002-P009-001` | 用一条代表性体验链检验质量目标和生产方式 |
| `S4 制作与内容生产` | Agile 的持续反馈；课程 `E-SJ002-P017-001` | 在可控范围内批量生产，并让设计、内容和测试保持同步 |
| `S5 Alpha / 功能完整` | MDA 的系统回归；课程 `E-SJ003-P010-001`、`E-SJ003-P021-001` | 所有关键系统接通后暴露二阶影响和回归风险 |
| `S6 Beta / 发布候选` | Steamworks 的平台核对；课程 `E-SJ002-P019-001` | 冻结内容、分级问题、完成平台和质量检查 |
| `S7 发布、运营与复盘` | Steamworks 的上线准备；Agile 的持续反思 | 发布后观察、支持、复盘，并决定修复、迭代或结束 |

这里的“采用”是本知识系统的工作标准，状态为 `Proposed baseline`。它不代表外部来源共同声明了 S0-S7，也不代表当前卡牌项目已经通过任何阶段门。

## 5. 对当前项目的使用方式

当前项目是“唯一核心卡 + 通用辅助卡 + 组合规则 + 共享世界 + 回合制对战”。建议这样使用三类框架：

- 用 MDA 表检查一条核心卡/辅助卡组合：规则是什么，会诱发什么选择，玩家应感到什么；如果动态与体验承诺冲突，回到设计假设。
- 用迭代原则安排一次只回答一个主要未知的原型，并在每轮后记录观察、解释、改动和回归范围。
- 用平台发布清单检查构建、商店信息、上线配置和已知问题；这些检查进入代码开发/发布记录，不写入 GDD 玩法正文。

## 6. 尚未确认与复审条件

1. `S3` 与 `S4` 的具体质量阈值、内容量和团队规模没有外部统一答案，仍为 `Unknown`。
2. Steamworks 文档只适用于 Steam；目标平台改变时必须重新读取对应官方要求。
3. MDA 是分析语言，不保证可以仅靠纸面推理预测真实玩家体验；必须由 `E3` 原型或试玩证据校验。
4. Agile 原则不要求某种固定工具、会议或迭代时长；本仓库不把工具偏好写成硬规则。
5. 下次阶段模型重大修改、目标平台变化或新增独立研究来源时复审本文，并保留旧版本。
