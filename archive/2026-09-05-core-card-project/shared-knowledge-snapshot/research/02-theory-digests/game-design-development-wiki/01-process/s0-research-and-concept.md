## 一句话结论

先把“为谁解决什么问题”说清，再把概念压缩成可复述的核心循环、设计支柱和范围边界。S0/S1 的完成不是写出漂亮设定，而是让一个没有参与讨论的人能复述玩家要做什么、为什么值得验证，以及现在明确不做什么。

## 初学者解释

一个点子通常同时包含愿望、参考作品和未经验证的假设。S0 把它们拆开，S1 再把仍然值得验证的部分组织成概念。不要一开始写全部卡牌、地图或剧情；那些细节会遮住真正未知。

```text
问题/机会
  -> 目标玩家与情境
  -> 核心动作与体验承诺
  -> 设计支柱、反支柱与范围
  -> 最大风险与最小验证
  -> GDD-0 / Proposal
```

## 为什么重要

- 没有目标玩家，所谓“好玩”没有判定对象。
- 没有核心动作，功能清单无法说明玩家为何会回来。
- 没有范围边界，预制作会把所有未知推迟到昂贵的制作阶段。
- 没有风险和验证信号，概念文档只能表达信心，不能指导下一步。

## S0 的执行步骤

### 1. 写出问题陈述

用一句话说明要改善的玩家处境或制作机会：

> 对【目标玩家】来说，在【情境】中，【现有体验/空白】导致【问题】；本项目想让他们通过【核心动作】获得【可观察结果】。

问题不能只写“做一款很有趣的游戏”。如果暂时只能写愿望，状态应为 `Unknown` 或 `Raw Idea / Unqualified`，先进入 `idea-inbox/`。

### 2. 描述目标玩家和情境

至少记录：

| 字段 | 要回答的问题 |
| --- | --- |
| 经验与偏好 | 玩家已经熟悉哪些规则？喜欢规划、适应还是即兴？ |
| 使用情境 | 每次玩多久？独自、合作还是竞争？在哪种设备上？ |
| 核心动机 | 想掌控、探索、表达、收集、竞争还是放松？ |
| 非目标体验 | 当前不优先服务哪种玩家或行为？ |

玩家类型是工作假设，不是人口统计事实。`SJ-002` 对休闲/中度/硬核的分类属于讲师启发式，必须用本项目测试校验（`E-SJ002-P006-001`）。

### 3. 压缩概念

使用以下句式，让读者在 30 秒内复述：

> 玩家作为【身份】，在【场景】中反复【核心动作】，为了【目标】承担【关键取舍】，并获得【核心体验】；独特约束是【差异点】。

概念应包含核心动作、目标、代价和差异点，不应把营销口号或完整世界观当作核心循环。

### 4. 选择 3—5 个设计支柱（Wiki Inference / 建议范围）

`3—5` 是本 Wiki 为保持可记忆、可取舍而采用的建议工作范围，不是课程原话、行业定律或阶段门硬阈值。项目可以使用更少或更多支柱，但必须说明为何仍能约束设计选择。

每个支柱都要能约束取舍：

| 设计支柱 | 玩家可观察表现 | 支持规则 | 反面信号 |
| --- | --- | --- | --- |
| 有意义的构筑取舍 | 玩家比较组合并解释放弃了什么 | 费用、标签和有限槽位 | 最优解明显，选择只变成点按钮 |
| 核心身份持续存在 | 玩家能说出核心卡为何值得保留 | 核心卡不可资源化、组合标签 | 核心卡只是一次性资源 |

“深度”“沉浸”“专业”不是支柱，除非补充玩家会做什么、看到什么和改变什么决定。

### 5. 写反支柱和范围

反支柱帮助团队快速排除看似合理但会稀释体验的方案。例如：

- 不以卡池数量代替组合空间，因此系统未验证前不批量制作卡牌。
- 不让代码现状决定玩法规则，因此实现差异写入开发进度和设计偏差记录。
- 不把共享世界做成与核心卡无关的独立经营游戏，因此每个外围系统都要说明它如何改变构筑或冲突动机。

### 6. 列出最大未知和最小验证

一次只选择一个主要未知，格式如下：

| 字段 | 示例 |
| --- | --- |
| 假设 | 玩家愿意围绕一张唯一核心卡反复尝试不同辅助卡组合。 |
| 最小验证 | 六张示例卡、一次费用结算、一个胜负反馈的纸面或数字原型。 |
| 成功信号 | 新玩家完成循环，并能解释组合代价和下一次尝试。 |
| 失败信号 | 玩家只记住美术/故事；无法说明核心卡价值或下一步选择。 |
| 下一步 | `Go`、`Iterate`、`Park` 或 `Stop`，附证据链接。 |

## S1 最小产出

- 一页概念 brief：目标玩家、平台/模式假设、核心动作、体验承诺、差异点。
- 核心循环图：进入处境 → 读取信息 → 选择并支付代价 → 结算反馈 → 再次选择或结束。
- 设计支柱与反支柱：每项都连接可观察行为。
- 范围表：包含、明确不包含、触发重新讨论的条件。
- `GDD-0` 或 Proposal 草稿：标出 `Confirmed / Hypothesis / Unknown / Out of Scope`。
- 最大风险和最小验证计划。

## 正例与反例

**正例：**

> 在共享世界获得两张辅助卡后，玩家必须在保留资源、主动挑战或交易之间选择；这可能让唯一核心卡的身份影响世界路线。先用一条组合链验证玩家是否理解代价，外围经济暂不展开。状态：`Hypothesis`。

**反例：**

> 这是一个有地图、交易、AI 卡牌、Boss、剧情和丰富成长的沉浸式卡牌宇宙。

反例列出了系统名和形容词，却没有玩家反复做什么、为何选择、哪个未知最值得先验证。

## 阶段门：S1 → S2

判定为 `Go` 需要：

- 未参与设计的人能复述目标玩家、核心动作、目标、代价和独特约束。
- 核心循环至少有开始、行动、反馈、失败/退出和再次进入动机。
- 当前范围内的主要未知不超过一个优先级最高的问题，且有可观察成功/失败信号。
- 相关素材已审查；`idea-inbox/` 内容没有直接进入正文。

否则使用：

- `Iterate`：概念可能成立，但玩家、循环或验证信号仍含糊。
- `Park`：当前价值不足以投入原型，但保留复议条件。
- `Stop`：核心问题与目标、成本或可行性不可接受，并记录失败路径。

## Wiki 推断（Inference）

本页将来源主张组织为“问题 -> 玩家与情境 -> 概念 -> 支柱/反支柱 -> 主要未知 -> 最小验证”的工作顺序。支柱数量、概念句式和 S1 产出组合是便于初学者执行的建议结构，需按项目规模和风险调整。
